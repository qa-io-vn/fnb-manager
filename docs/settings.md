# Settings sources

How the settings pages read and write their data, in the live app and in the demo. Every page goes through the sources below and one mutation hook. Each failure therefore has its message, the audit line has its columns, and cached numbers are dropped after a save. The page tickets build on this (#159 to #164, Nhân viên in #214, Checklist in #220, Khách hàng thân thiết in #240 and its Ưu đãi tab in #270). The rules for who may write what are in [schema.md](schema.md#who-can-write-what) and [api.md](api.md#34-settings-and-writes); [Who may write what](#who-may-write-what) below says how every page shows them and what the live specs of #165, #214, #220, #240 and #270 prove for each login.

`SettingsSourceProvider` (`settings-source-context.tsx`) loads the sources of the current mode together, lazily, when a page first asks. `useSettingsSourceState()` then answers `{ status: "ready", source, manual, staff, operations, loyalty, customers, rewards }`. Like the analytics source, a failed load is tried again when the next page asks, or on "Thử lại". The demo implementations of the first three write into the session's `DemoSettingsStore` (`apps/web/src/demo/demo-settings.ts`). The demo report engine reads that same store, so a saved change moves the demo's numbers at once. A demo page says `settings.demoNote`: changes last for the session only. The four later sources serve the staff app's records and the loyalty programme, which the demo does not have: `operations` and `customers` are `null`, so their pages show a plain state instead of figures, and the demo's `loyalty` and `rewards` answer a fixed sample and refuse every write with `forbidden`, so their pages show it read-only ([The demo's rows](#the-demos-rows)). The pages outside Settings that read these sources (Vận hành, Khách hàng and the operations cards on two themes) are described in [web-app.md](web-app.md#phase-14b-decisions).

### Live writes

- **One statement per save.** Each save is one statement, so it succeeds or fails as a whole:
  - costs, fee rates, targets, roles and thresholds: one PostgREST upsert on the table's unique key (`onConflict`), including a CSV import of up to 2,000 rows;
  - profiles: one update of the columns given; an empty change sends nothing and answers the stored row;
  - holidays and new legal drafts: one insert; a draft's patch: one update; publication and retirement: one function call;
  - the staff roster, the staff revenue visibility, the staff contact note and pairing codes: one function call each. These functions check the caller themselves and raise `42501` or `22023`, so a refused staff write is always an error, never an answer with no row;
  - checklist templates: one call of `save_checklist_template` per save (the template and all its items, as one new version) or of `set_checklist_template_active`, refused the same way;
  - the loyalty programme: one insert or one update of `loyalty_programmes` that returns the row; a staff phone: one insert, or one delete that returns the deleted id, so a delete that row-level security ignored is reported as `forbidden`;
  - rewards: one insert or one update of `coupons` with its terms, and a status change as one update of `status` alone; the database's triggers decide the rest (the cap, the approval, the return to draft, the rail and mapping checks).

  The exception is overrides. The rows that are set go in one upsert, then the cleared ones go in one delete per POS account, so a failure can leave part of the save written. The pages save overrides with `touchesMappings`, which drops the cached settings and analytics after a failure too.
- **A key twice in one batch.** A batch that names the same key twice fails whole: Postgres answers `21000`, reported as `duplicate`, and the demo refuses it the same way.
- **Tenant-wide rows.** A tenant-wide row (null `store_id`) resolves through the nulls-not-distinct key. A tenant-wide and a store row of the same item and date are therefore two rows, and saving the same scope again updates its row. `e2e:live/settings-manual` proves this through supabase-js on the local stack, so no RPC fallback is needed.
- **Reads.** Reads page through the 1,000-row cap in a stable order (`fetchAllPages`).
- **Refused writes.** Row-level security answers a refused update or delete with no row, not an error, so:
  - an update that returns no row is reported as `forbidden`;
  - a delete that removed nothing is checked by a second read. If the row is still there, the delete was refused (`forbidden`). A published legal text gives `frozen` instead.

## Errors

`SettingsWriteError` carries a `code` and, when the database named one, the `constraint`:

| Database answer | Code |
|---|---|
| `42501`, `PGRST3…` | `forbidden` |
| `23505` | `duplicate` (with the constraint) |
| `21000` (one batch naming a key twice) | `duplicate` |
| `23514`, `22023`, any other SQLSTATE | `invalid` (with the constraint when named) |
| `55000` (a published legal text) | `frozen` |
| no answer (the request never reached the server) | `network` |

The demo raises the same codes:

- A refused demo write becomes `invalid`, a duplicate `duplicate`, and a frozen legal text `frozen`.
- The constraint is the refused field's name. A store code another store uses and invalid opening hours are reported under the database's own constraint names (`stores_code_unique_in_tenant`, `stores_opening_hours_valid`), so the demo shows the same messages as the live app. Store codes are compared trimmed and upper-cased, as the database does.

An error that is not a `SettingsWriteError` counts as `network`. That includes a row the database stored but whose answer no longer parses. A retry then resends the same upsert, which writes nothing new.

The Nhân viên page names its refusals itself, from the code above (`staffErrorKey` in `src/settings/staff/staff-rules.ts`, `revenueErrorKey` in `src/pages/settings/nhan-vien-page.tsx`):

| Action | `forbidden` (`42501`) | `invalid` (`22023` and other checks) | `network` |
|---|---|---|---|
| Add or edit a person | `settings.staff.error.scope`: you add or edit staff only in the stores you manage | `settings.staff.error.invalid`: the name, role or stores are not valid | `settings.error.network`, with "Thử lại" in the form |
| Deactivate or reactivate | `settings.staff.error.rowForbidden`: the person works in a store outside your scope | `settings.staff.error.invalid` | `settings.error.network`, with "Thử lại" under the list |
| Issue a pairing code | `settings.staff.pairing.error.forbidden`: the person works in a store outside your scope | `settings.staff.pairing.error.invalid`: the person is deactivated, or their login is an owner, viewer or publisher of the tenant | `settings.error.network`; pressing "Tạo mã ghép nối" again asks for a new code |
| Save the revenue level | `settings.staff.revenue.error.forbidden`: only an owner with every store changes it | `settings.error.invalid` | `settings.error.network` in the save bar; the choice stays, so Lưu sends it again |

`issue_pairing_code` also answers `42501` for a row that does not exist, so an unknown row reads like a forbidden one. The source never accepts a code that is not six digits: such an answer counts as `network`.

The pages of 14b and phases 16 to 18 name their refusals the same way:

| Action | `forbidden` (`42501`) | `invalid` (`22023` and other checks) | Other answers |
|---|---|---|---|
| Save the staff contact note (`contactErrorKey`, `nhan-vien-page.tsx`) | `settings.staff.contact.error.forbidden`: only an owner with every store changes it | `settings.staff.contact.error.invalid`: at most 500 characters, text and line breaks only, no link | `settings.error.network` in the save bar, the text kept for Lưu |
| Create, edit, copy, retire or reactivate a checklist (`checklistErrorKey`, `checklist-rules.ts`) | `settings.checklists.error.scope`: only your stores' checklists; a checklist of every store needs every store | `settings.checklists.error.invalid`: check the title, items and units | `settings.error.network`, with "Thử lại" in the form or under the list |
| Save the loyalty programme (`refusalStatusKey` and `refusalIssueOf`, `programme-form.tsx`) | `settings.error.forbidden` | a `22023` that names a column (`refusedProgrammeField` of `src/loyalty/programme-columns.ts` reads the column from the message) shows `settings.loyalty.error.refused` under that field; the launch hold shows `settings.loyalty.hold.refused` under Trạng thái, and nothing is saved | `23505` on the one-active-programme index: `settings.loyalty.error.otherActive` under Trạng thái; a lost connection `settings.error.network` |
| Add or remove a staff phone (`staffPhoneErrorKey`, `staff-phones.tsx`) | `settings.error.forbidden` | on add, `settings.loyalty.phones.invalid` | on add, `23505` reads `settings.loyalty.phones.duplicate`; otherwise `settings.error.<code>` |
| Save a reward or change its status (`rewardWriteError`, `supabase-rewards-source.ts`; `REFUSAL_KEYS`, `reward-form.tsx`) | the trigger's "only an owner with every store approves": `settings.rewards.refusal.ownerApproves` on Trạng thái | the trigger's message names the refusal and its field: over the cap (`settings.rewards.refusal.cap` on the percentage, `.amountCap` on the amount), a minimum bill missing for an amount off, an unknown or overlapping item, a retired reward (`.retiredFinal`), a store without a rail (`.noRail`) or without this reward's POS mapping (`.noMapping`), an active reward's mapping (`.keepsMapping`), the store list (`.storeScope`); a named constraint shows `.value` on its field | `23505` on the reward key: `settings.rewards.error.duplicateKey`; a lost connection `settings.error.network` |

## `useSettingsMutation`

Pages call writes only through `useSettingsMutation(write, options)`. The `write` receives the settings source, the tenant id, the page's arguments, the manual source, the staff source and, since `631aec0`, the operations source (`null` in the demo); the loyalty and reward writes reach their sources through `useSettingsSourceState()` inside the page's `write`. A pairing code is not a write: the page calls `issuePairingCode` directly, so the code never passes through the mutation's arguments, its retry or the query cache.

- **After a success** it invalidates the tenant's settings queries, its cached analytics and Hôm nay's report (`invalidateTodayReport`, the `today` queries of the tenant), since a holiday (Hôm nay's excluded days) or a payment-kind change moves Hôm nay's numbers too. A write that touches a mapping (`touchesMappings`) also starts the catch-up.
- **After a failure** it invalidates nothing, except after a mapping save, which may have written part of its rows: then it drops the settings, the analytics and Hôm nay's report.
- **`errorKey`** is the message to show:
  - `settings.store.hours.ownerOnly` when `forbidden` and `touchesOpeningHours(args)` says the change held opening hours;
  - `settings.store.code.duplicate` for `stores_code_unique_in_tenant`;
  - `settings.store.hours.invalid` for `stores_opening_hours_valid`;
  - `settings.manual.costs.amountRefused` for `item_costs_amount_whole_dong` (`23514` from the database check on `item_costs.cost_amount`, whole đồng from 0 to 100,000,000; the Giá vốn tab and the CSV import refuse the same values before sending);
  - `settings.fees.refused` for `payment_fee_rates_within_limits` and `settings.targets.refused` for `targets_amount_whole_dong`;
  - `settings.legal.frozen` for `frozen`;
  - otherwise `settings.error.<code>`.
- **`canRetry`** is true after a network failure, and `retry()` sends the same arguments again.

## Phân loại: item categories and payment kinds

The two 10b tabs of Settings → Phân loại write the override tables of the table above. Owners and managers with an unlimited scope may save them, like the roles (`useSettingsAccess("roles")`); every other member reads them as text with the read-only note and no save bar.

- **Nhóm của món** (`?tab=nhom-mon`) reads `items` and `itemTypes`, and `data_quality_items` through `useUncategorisedSales`.
  - "Chưa phân loại" lists what Thực đơn and Chất lượng dữ liệu call uncategorised. The hook calls `data_quality_items` once per POS account, with the store ids of that account, over the 90 days ending on the last complete day. Since the function reports each item under the account of the first store asked that sold it, every row of such a call carries that account in `pos_account_id`.
  - The hook keeps the rows with `type_known`, `catalogue_modifier` and an override all false or null (`isUncategorisedItem` of `@fnb/reports`, the predicate Chất lượng dữ liệu's uncategorised card uses too, so both pages agree), in the function's order (net amount, highest first, across the accounts). Each row is joined to `items` by POS account and item key, the key of the sale lines (`coalesce(item_external_id, item_name)`). An item sold without an id therefore gets an entry of its own, outside the catalogue, and its override is saved under that key.
  - An item whose override the cached `items` already hold leaves the list at once, before the function is read again. The call goes through the cached analytics path, so the save's `invalidateAnalytics` reads it again. While it loads the list says so; if it fails, it offers "Thử lại".
  - Then come the saved overrides, those whose item left the catalogue included, so they can be cleared. Last is a search over every item, the uncategorised first.
  - Each item offers "Theo POS" and the item types of its own POS account, never another account's and never free text. Saving sends the changed items to `saveCategoryOverrides`; "Theo POS" is a null type, so it deletes the override.
- **Loại thanh toán** (`?tab=thanh-toan`) reads `paymentMethods`. It shows each method under its POS account with the POS kind (`pos_kind`), the override and the kind in effect. Saving sends the changed methods to `saveKindOverrides`; "Theo POS" is a null kind, so it deletes the override. The tab notes that the expected cash of past shifts changes only after those days are synced again.
- **After a save.** Both tabs save through `useSettingsMutation` with `touchesMappings`, so:
  - the tenant's settings and analytics are invalidated, and the next report read shows an item in its new type, an in-app navigation back included;
  - the catch-up starts for members who may refresh, and its banner shows on every settings and theme page while days are pending; when the runner finishes it says "Đã cập nhật xong số liệu theo thay đổi cài đặt." until it is closed;
  - the cached list takes the saved overrides at once, so the page shows them even if reading them back fails.

  In the demo the store re-ingests at once, so the banner never shows.
- **Errors.** The save bar shows the message of `errorKey`. After a network failure a "Thử lại" button calls `retry()`, which sends the same changes again.

## Ngưỡng báo cáo: the Khuyến mãi field

Ngưỡng báo cáo shows the nine `report_settings` columns in four groups: Thực đơn, Tiền mặt, Giờ and, since #191, Khuyến mãi with "Số tuần trước khuyến mãi" (`promoPreWeeks`, `promo_pre_weeks`: 2 to 8 weeks, default 4). Its hint and default show like the others' ("Mặc định: 4 tuần."), a value outside 2 to 8 is refused with "Nhập giá trị từ 2 đến 8." before anything is sent, a refusal by `report_settings_promo_pre_weeks_check` is shown on the field, and "Khôi phục mặc định" sets it back to 4 with the rest. It is saved like any other threshold, through `saveReportSettings` and `useSettingsMutation`, so the cached analytics are dropped at once.

Khuyến mãi's lift card reads the field through `report_settings_of` and passes it to `promotion_lift` as `pre_weeks` (the function also falls back to it when a call leaves `pre_weeks` out), so the call and the card's subtitle use one value and a saved change asks for a new lift: the `prior_weeks` comparator averages that many weeks before the first promotion day, and `sister_store` compares both the promoting and the control stores with that many weeks before. The demo engine reads the same field from the session's `DemoSettingsStore`, and the lift card names the weeks in its subtitle, so the next view shows the change in both modes.

## Dữ liệu nhập tay: item costs

`#/cai-dat/du-lieu-nhap-tay` (`src/pages/settings/du-lieu-nhap-tay-page.tsx`) holds the manual data in three tabs: Giá vốn (`?tab=gia-von`, the default, #161), Mục tiêu (`?tab=muc-tieu`) and Phí thanh toán (`?tab=phi`, #163; see the next section). [manual-data.md](manual-data.md) describes the costs, their scopes, dates and history; this section says how the tab uses the sources.

- **Reads.** `useItemCosts` (every row, so the history), `useItems` and `useItemTypes` (the catalogue, its sizes, prices and categories), and `item_summary` over the last 90 days of the scope's stores through the cached analytics path (`useItemSales` in `src/settings/manual/use-item-sales.ts`), so a save's `invalidateAnalytics` reads it again.
- **Writes.** "Lưu" sends the typed costs of the scope to `saveItemCosts` in one call; "Xóa" in an item's history calls `deleteItemCost`. Both go through `useSettingsMutation` without `touchesMappings`: costs are read at query time, so no catch-up starts, and the tenant's cached analytics are dropped after a success, so Thực đơn shows the new margins on its next view. The saved rows replace the cached `itemCosts` at once, and a deleted row leaves it.
- **Access.** `useSettingsAccess("manualData", storeId)`: a store row needs an owner or manager with the store in scope, a row for all stores an owner or manager with an unlimited scope (`settings/access.ts`), as the policies of `item_costs`, `targets` and `payment_fee_rates` say. The targets and fees tabs of #163 use the same area.
- **Checks.** `itemCost(fractionDigits)` in `src/settings/validation.ts`: 0 to 100,000,000 (`ITEM_COST_MAX`), whole đồng for VND; `readCostText` also reads `8333.33` or `25.5` as a fraction of a đồng instead of "not a number"; dates through `businessDate`. The database has no check on `cost_amount` yet; it comes with #162.
- **Order of reads.** The tab waits for the membership before it picks the default scope and asks for the 90-day sales, so a store-limited member reads their store's sales only.
- **Delete refusals** have their own words (`deleteErrorKey`: `settings.manual.costs.deleteError.forbidden`, `.network`, `.other`); after a lost connection "Thử lại" calls the delete mutation's `retry()`.

## Dữ liệu nhập tay: targets and fee rates

[manual-data.md](manual-data.md) describes both tabs; this section says how they use the sources.

- **Mục tiêu** (`src/settings/manual/targets-tab.tsx`) reads `useTargets`, `useMembership` and `month_pace` for the chosen store and its current month through the cached analytics path (`useMonthPace`). "Lưu" sends the changed months to `saveTargets` through `useSettingsMutation` without `touchesMappings` (targets are read at query time); the saved rows replace the cached `targets`.
- **Phí thanh toán** (`src/settings/fees/fees-tab.tsx`) reads `usePaymentMethods`, `useFeeRates` and `useMembership`. "Lưu" sends the typed rates of the scope to `saveFeeRates` through `useSettingsMutation` with `touchesMappings`, because the refresh writes the fee estimates: the trigger on `payment_fee_rates` widens the pending range and the save starts the catch-up, as a mapping save does. The saved rows replace the cached `feeRates`.
- **Access.** Both use `useSettingsAccess("manualData", storeId)`; a target always has a store.
- **Checks.** `targetAmount` (1 to `TARGET_MAX`, whole đồng), `percentage()` for the fee rate (0 to 20 %, three decimals), `feeFixedAmount` (0 to `FEE_FIXED_MAX` = 100,000), all in `src/settings/validation.ts`; `readMoneyText` (`src/settings/forms/money-text.ts`) reads `25.5` as a fraction of a đồng, as `readCostText` does. They are the limits of the database checks `payment_fee_rates_within_limits` and `targets_amount_whole_dong`, whose refusals (23514, `invalid` with the constraint) read `settings.fees.refused` and `settings.targets.refused` through `CONSTRAINT_MESSAGE_KEYS`; the demo store raises the same constraint names.
- **Loading.** Both tabs show `SectionLoadState` (`src/settings/section-load.tsx`) until their reads arrive, with "Thử lại" after a failure.

## Queries

`apps/web/src/settings/queries.ts` has one hook per read: `useMembership`, `useItemTypes`, `useReportSettings`, `useCatchUpStatus`, `useTenantProfile`, `useTenantDefaultLanguage`, `useStoreProfiles`, `useItems`, `usePaymentMethods`, `useFeeRates`, `useHolidays(year)`, `useItemCosts`, `useTargets` and `useLegalDocuments`, and for Nhân viên `useStaffRoster`, `useStaffRevenueVisibility`, `useStaffApps` and `useStaffContact` (areas `staffRoster`, `staffRevenue`, `staffApps` and `staffContact`, read through the staff source). Since 14b the read also receives the operations and loyalty sources: `useChecklistTemplates` (area `checklistTemplates`, rejected with "no operations data in this mode" in the demo), `useLoyaltyProgrammes` and `useLoyaltyStaffPhones(enabled)` (areas `loyaltyProgrammes` and `loyaltyStaffPhones`); `src/settings/rewards/queries.ts` adds `useRewards`, `useRewardRails` and `useRewardDiscountDays(rewardId, year, enabled)` under the same keys (areas `rewards`, `rewardRails` and `rewardDiscountDays`, with the reward and year as parts).

Their keys are `["settings", sourceKind, tenantId, area, ...parts]`, with the year as a part for holidays. So `invalidateSettings(queryClient, tenantId)` drops every settings read of the tenant at once.

## The demo's rows

- **Order.** Lists come back in the live order (costs by item, store with tenant-wide first, date; fee rates by method, store, date; targets by store, period kind, start; legal texts by kind, language, version), so a page shows a new row in the same place in both modes.
- **Ids.** Demo rows have no database ids. Each row's id is built from its key, such as `fee:<store>:<method>:<date>`. A legal draft's id follows its version, so a draft whose version is changed comes back under a new id.
- **Audit line.** It shows "you" with the time of the session's last save that changed that row. Rows from the demo's defaults have none, and a save that changes nothing stamps nothing, as the profile triggers do live.
- **Legal texts.** Publication and retirement follow the database's functions. Publishing a draft retires the text it replaces, and a published or retired text is never edited or deleted.
- **Staff.** `demo-staff-source.ts` keeps its own state beside the session's `DemoSettingsStore`: four neutral sample people across the two demo stores, one in each state the page shows ("Nhân viên 1", a paired staff member with the phone hint `…204`; "Nhân viên 2", waiting to pair; "Quản lý 1", a paired manager of both stores; "Nhân viên 3", deactivated), with pairing and deactivation dates before the demo's as-of day, and the revenue level `all`. Adds, edits, deactivations, reactivations and the revenue level last for the session and stamp the audit line; a deactivation drops the phone hint and the pairing, and a reactivation puts the person back to waiting. It refuses what the database refuses with the same codes (`staffChangeProblem`: a name of 1 to 100 characters without control characters, the role staff or manager, 1 to 50 known stores listed once, or every store). Its pairing codes are six random digits from `crypto.getRandomValues`, valid ten minutes and kept nowhere; a deactivated person gets `invalid` and an unknown row `forbidden`. It has no staff Mini App, so the QR section shows its empty state. Its contact note starts as a sample (`DEMO_STAFF_CONTACT`) and can be changed or cleared for the session, with the page's own checks (`staffContactIssue`) refused as `invalid`.
- **Checklists.** The demo has no operations source, so Cài đặt → Checklist shows `settings.checklists.demo` (the demo has no staff app) and no list or form.
- **Loyalty and rewards.** `demo-loyalty-source.ts` answers one programme (`DEMO_PROGRAMME`: "Tích dấu 8 ly", 1 December 2026 to 30 November 2027, a reward budget of 20,000,000 ₫, a draft whose notification decision is pending, the default parameters of `@fnb/core`) and two synthetic staff phones (`0900000101` with a note, `0900000102`), and `demo-rewards-source.ts` a sample catalogue of three rewards (an active free drink at the first demo store, an approved 20 % bill discount and a draft free upgrade) with a fallback rail and two POS mappings at the first demo store only, so the second store shows why a reward cannot be activated there, and no discount days. ## The Cửa hàng page

`#/cai-dat/cua-hang`, the page the settings open on (`src/pages/settings/cua-hang-page.tsx`, forms in `src/settings/store/`).

- **The business block** holds the legal form (household business, micro-enterprise, small enterprise, other enterprise, not yet known; one dated line says it decides the dossier for transferring personal data abroad, ADR-019) and the default language (Tiếng Việt or English).
- **One block per store** the member can see. The name, address, time zone and business-day start are text marked "lấy từ POS", with no control: the master-data sync overwrites the first three, and the day start fixes the business date of every sale. The block edits the store code, the opening date, the opening hours, the seats, the e-invoice status, the receipt numbering and the member feature on the POS. Under the receipt numbering the page names what `data_quality_summary` suggests (`receipt_restarts_daily`): whether at least 90 % of the days with numeric receipt numbers, over the 120 days up to the last complete day, start at 3 or below. It needs at least 20 such days and shows nothing otherwise; "Dùng gợi ý" appears when they restart daily and stays, unavailable, once applied. The demo's receipt numbers are not numeric (`HD…`), so the demo never shows a suggestion; the live check of `e2e:live/settings` shows it on the fixture tenant.
- Each block has its own save bar and audit line, and sends only the fields that changed. A store whose opening hours were never entered (null) says so above the days, which the editor shows as closed. A line under the opening hours says that saving them changes Giờ & ngày, Hôm nay's opening-hour figures, the incremental sync's schedule and the digest's time.

### Who may change what

| Block | May save | Everyone else |
|---|---|---|
| Business | an owner with an unlimited scope (`useSettingsAccess("tenantProfile")`) | reads it with `settings.store.tenant.readOnly` |
| Store, except the opening hours | an owner or manager with the store in scope (`useSettingsAccess("storeProfile", storeId)`) | reads it with `settings.store.readOnly.role` or `.scope` |
| Opening hours of a store | an owner with the store in scope (`useSettingsAccess("openingHours", storeId)`) | a manager reads them with `settings.store.hours.readOnly`; the rest of the block stays editable |

Row-level security and `app.stamp_store_profile` decide regardless: a refused hours change shows `settings.store.hours.ownerOnly`, a code another store uses `settings.store.code.duplicate` (also under the code field), and invalid hours `settings.store.hours.invalid`.

### Checks before a save

`src/settings/validation.ts`: `storeCode` (at most 12 characters once trimmed; an empty code is saved as none), `seatCount` (whole seats from 0 to 5,000; empty is unknown), `openingDate` (from 2000-01-01, so an older store can record its opening, to the end of next year) and the opening-hours editor's own check of each span. A change with a problem keeps the save bar's "Lưu" unavailable.

### The default language

`PreferencesProvider` keeps the device's language in storage only once the member chose it with the toggle, marked `languageChosen: true`. A Vietnamese an earlier version stored without that marker counts as not chosen (it was saved with every other preference), while an unmarked English is kept, since only the toggle could have stored it. Until a language is chosen, `TenantDefaultLanguage`, mounted in the shell, reads `defaultLanguage` (the column `tenants.default_language` alone, without the audit's member reads) and applies it through `adoptDefaultLanguage`, so a new session opens in the tenant's language and the toggle still wins on that device. It follows the tenant's language while the session runs too: an owner who never chose a language sees the app switch as soon as they save another default.

## The Ngày lễ page

`#/cai-dat/ngay-le` (`src/pages/settings/ngay-le-page.tsx`, parts in `src/settings/holidays/`). It reads `holidays(year)` through `useHolidays(year)`.

- **The year.** A select of 2024 to 2030 (`HOLIDAY_YEARS`, the range of the analytics calendar) opens on the current year in the tenant's time zone, held inside that range; its hint says the national calendar is shipped for 2024 to 2028 only. The page reads one year at a time. While a year loads, the Ngày nghỉ riêng section, its form and its status line stay mounted and only its list waits.
- **Ngày nghỉ riêng** (the tenant's own days, kind `custom`) comes first, because it is the part a member acts on. Each row shows the name as typed, the weekday and date, and the audit line (`AuditLine`: "Bạn" or the role). A note says that these days are left out of baselines and forecasts. The live functions exclude them at query time through `app.is_excluded_day`, and the demo engine at once, so the next view of a report shows the change.
- **Adding** takes a date from 2024-01-01 to 2030-12-31 (`HOLIDAY_DATE_BOUNDS`) and a name of 1 to 80 characters once composed and trimmed (`holidayName` and `holidayNameValueOf` in `validation.ts`: the name is normalised to NFC first, so a letter typed with combining marks counts once). `readHolidayDraft` sends that composed, trimmed name and holds back a name the date already has in the year on screen, compared in the same form ("Ngày này đã có ngày nghỉ riêng cùng tên."). The database's own refusal of a duplicate (`23505` on `holidays_tenant_country_date_name_key`, or the demo's duplicate) reads `settings.holidays.add.duplicate`. A successful add, whether from **Thêm** or from "Thử lại" after a lost connection, takes the same path: the form empties (a counter the form watches) and a day of another year moves the select to that year. **Xóa** on a row deletes it. Each action reports its outcome in one status line that stays mounted ("Đã thêm …", "Đã xóa …", or the refusal), with "Thử lại" after a lost connection (`retry`). After a delete, or an add sent again by "Thử lại", the focus moves to the section's heading when it would otherwise fall to the page.
- **After a save** the cached year takes the stored row at once (`withAddedHoliday`, `withoutHoliday`), and `useSettingsMutation` drops the tenant's settings, analytics and Hôm nay's report, so a Ngày report or Hôm nay opened next leaves the day out of its same-weekday baseline (the chip then reads "so với mức nền (7/8 tuần)" when one of the eight weeks is gone).
- **Ngày lễ quốc gia** lists the national days of the tenant's country for the year, read-only: the name in the interface language (`globalHolidayNameKey` maps the 13 names of the calendar; a name it does not know shows as stored), the date and the kind (`report.holiday.public`, `report.holiday.tet`). A note says the national calendar is shipped for 2024 to 2028 (`nationalCalendarYears`, the years of `VIETNAM_HOLIDAYS` and of its migration), because its lunar-calendar days are worked out year by year; a year without national rows says so.
- **Who may change it.** Owners and managers with an unlimited scope (`useSettingsAccess("holidays")`), as row-level security allows. Everyone else reads both lists with `ReadOnlyNotice` and has neither the form nor Xóa. Live, the insert policy also requires `created_by` to be the caller, and the triggers set `updated_by`, so a holiday saved from the browser carries its author and an insert naming someone else is refused (`42501`).

## The Pháp lý page

`#/cai-dat/phap-ly` (`src/pages/settings/phap-ly-page.tsx`, components and rules in `src/settings/legal/`) shows the legal texts of `legalDocuments`; the lifecycle and the rules behind it are in [manual-data.md](manual-data.md#legal-documents-settings--pháp-lý).

Each version shows its status, title, label ("Mã phiên bản ghi khi đồng ý"), the database's dates (`publishedAt`, `retiredAt`, in the tenant's time zone) and, for a draft, the audit line. "Xem nội dung" shows the text through the preview.

- **Actions.** "Công bố" (drafts), "Ngừng áp dụng" (published) and "Xóa bản nháp" (drafts) each open a confirmation under the version (`confirm-panel.tsx`; Escape or "Quay lại" closes it and returns the focus). A publication or retirement the database refuses because the version is no longer a draft or no longer in force (`22023`, `invalid`; the demo refuses the same way), as after another tab's change or a retry whose first answer was lost, says `settings.legal.stale`; deleting a draft published meanwhile says `settings.legal.frozen`. The list is read again after every action, refused ones included, so its states and dates are the database's. A published or retired version has no edit or delete control, and a draft open in the editor shows no action of its own.
- **Access.** `useSettingsAccess("legal")`: an owner with an unlimited scope writes; every other member reads the page with `settings.legal.readOnly` and only "Xem nội dung".
- **Slots.** "Mục liên quan" names the customer consents and personal-data requests (phase 17a) and links to Cửa hàng for the legal form.

`#/cai-dat/khach-hang-than-thiet` (`src/pages/settings/khach-hang-than-thiet-page.tsx`; the programme in `src/settings/loyalty/`, the rewards in `src/settings/rewards/`; messages in `settings-loyalty` and `settings-rewards`), built in #240 (`4ec5f3f`) and #270 (`0ca91d3`) on the loyalty tables of #239, #242 and #269 ([api.md](api.md), [schema.md](schema.md)). Two tabs, as links with `aria-current`: Chương trình (`?tab=chuong-trinh`, the default, also for an unknown tab) and Ưu đãi (`?tab=uu-dai`).

### Chương trình

- **The programme shown.** The tenant's programmes are read newest first; the page shows the one running, else the paused, the draft or the ended one (`preferredProgramme`), and a select "Chương trình đang xem" when there are several. "Tạo chương trình" appears only while every programme has ended (or none exists), since the database keeps one running programme per tenant.
- **The form** (`programme-form.tsx`, fields in `programme-fields.ts`). Thông tin chương trình: the name (1 to 120 characters), the start and end dates (the end on or after the start) and the reward budget. Trạng thái: Bản nháp, Đang chạy, Tạm dừng, Đã kết thúc. Then every mechanic parameter of `LOYALTY_PARAMETER_RANGES` in `@fnb/core`, each with its unit, its range and its default in the hint: Tích dấu (stamps per card 2 to 20, default 8; the minimum bill, default 50,000 ₫; welcome stamps, default 2 and fewer than a full card; how long stamps last, default 6 months), Tích điểm (the amount per point, default 10,000 ₫; points per amount, default 1; point expiry, default 12 months), Giới hạn chống gian lận (earning invoices and receipt claims per phone per day, default 3 each, and up to 50 excluded order sources), Mã check-in và gửi hóa đơn (the check-in window, default 2 minutes before and 15 after; the member code's life, default 120 seconds; how long a check-in waits for its invoice, default 24 hours; the receipt-claim window, default 72 hours), and Giá trị điểm và dự phòng (a point's value, default 500 ₫, and the expected breakage, default 20 %). The draft is checked with `loyaltyProgrammeSchema` of `@fnb/core`, the schema the jobs use, before anything is sent; a field shows its message once touched or after Lưu.
- **The launch hold.** The last group records the decision on notifying the Department of Industry and Trade (Quyết định thông báo Sở Công Thương): Chưa quyết định, Đã thông báo Sở Công Thương, Dưới ngưỡng thông báo (a reward total under 100 million đồng) or Không phải thông báo (its legal basis then required, at most 500 characters), with the date of the decision (the day of saving when left empty), and links to Cài đặt → Pháp lý. While the decision is Chưa quyết định, a note says the programme is held ("Đang giữ chưa ra mắt…"), Đang chạy is refused under Trạng thái before sending, and the database refuses it again (`22023`, shown as `settings.loyalty.hold.refused`: "…chưa có gì được lưu."). Once a decision is recorded the note says the programme may run.
- **Saving.** Lưu sends the record and its parameters through `useSettingsMutation` as one insert or update; the stored row replaces the cached one at once (`withSavedProgramme`). A refusal that names a column shows next to that field ([Errors](#errors)). The note under the intro says a change applies from the next earn.
- **Số điện thoại nhân viên** (`staff-phones.tsx`). The exclusion list: invoices and receipt claims of these numbers earn nothing (the database refuses them on every earn path, and also the phones of active roster staff, `90_staff_phone_earn.sql`). Owners and managers see the section (`seesLoyaltyStaffPhones`); viewers and staff do not. Each number shows masked, `••• ••• 301` style with only its last three digits (`maskPhone`), with its optional note (at most 100 characters, no names) and the date it was added; the full number never appears in the page, the title or the address. "Thêm số" reads a national or international number through `normalizeLoyaltyPhone` of `@fnb/core` and stores it in E.164; a number already listed reads `settings.loyalty.phones.duplicate`. Add and remove are offered to owners and managers with every store (the `loyalty` area); a store-limited manager reads the masked list.
- **Members.** For those who may read the Khách hàng section (owners, managers and viewers), a link "Xem thành viên, sổ điểm và hàng chờ đối soát" opens `#/khach-hang/thanh-vien` ([web-app.md](web-app.md#phases-16-to-18-decisions)).
- **Access.** `useSettingsAccess("loyalty")`, the rule of `roles`: owners and managers with every store write; everyone else reads the form with `settings.loyalty.readOnly.role`, or `.scope` for a store-limited owner or manager, since the programme is the whole chain's.

### Ưu đãi

- **The catalogue** (`rewards-tab.tsx`, `reward-form.tsx`, rules in `reward-fields.ts`). The tenant's rewards with their kind, cost, status (Bản nháp, Đã duyệt, Đang áp dụng, Đã ngừng hẳn) and approval line ("Chờ chủ quán duyệt.", or who approved it and when). "Tạo ưu đãi" and a reward's form edit every field of `coupons`: the programme, the name (1 to 120 characters), the reward key (lower-case letters, digits, `-` and `_`, at most 64), the description (at most 500), the kind (Tặng món, Giảm theo phần trăm, Giảm một số tiền, Lên size hoặc thêm topping; the form says there is no cash, top-up or prepaid kind), the percentage (0.01 to 100) or amount, the reward items (at most 50, required for a free item) and excluded items (at most 100, never the same item in both), the cost in stamps (0 to 100) or points (0 to 1,000,000; at least one of them), the minimum bill, the validity dates, the voucher's life (1 to 365 days, default 30), the hold (1 to 168 hours, default 24), the per-member limit (1 to 100, or none) and the stores (every store, or 1 to 50).
- **The 50 % cap.** For a percentage or an amount off, the form takes the cap of `promotionRules` in `@fnb/core` in force over the reward's validity (from its first day, or today, to its last; the lowest rate when several versions overlap, `rewardCapOf`) and refuses, before sending, a percentage above it or an amount above the cap times the minimum bill, which must then be set; the message names the rate and its legal basis. The database checks the same dated cap again (`20261119300000_coupon_catalogue.sql`, held equal to the code by `92_discount_cap_mirror.sql`), and its refusal shows on the same field.
- **Rails and readiness.** For each store the reward applies to, the form shows the store's coupon rail in force (Chiết khấu thanh toán trên POS, Mã từ kho mã CRM, Mã kiểm tra qua CRM) and this reward's mapping (the POS discount name, the zero-price item or the CRM programme), or why it is not ready ("Chưa có kênh ưu đãi", "Chưa gắn với chiết khấu trên POS") and so cannot be activated (`readinessOf`). The web app does not write rails or mappings; setting them up in the POS and trying them at the till is #246.
- **Status and approval.** `actionsOf` offers, to those who may write: Duyệt on a draft (an owner with every store only, `useSettingsAccess("rewardApproval")`), Kích hoạt on an approved reward, Tạm ngưng on an active one, and Ngừng hẳn on any reward not retired, after a confirmation that it cannot be reopened. A change to the terms of an approved or active reward by someone who may not approve sends it back to draft for the owner, and the form says so before Lưu (`sendsBackToDraft`; the database's trigger does the same). A retired reward keeps a read-only form and "Ưu đãi đã ngừng hẳn thì không mở lại được.".
- **Discount days.** Under a saved reward, "Số ngày giảm giá năm {year}" lists `coupon_discount_days` for the current year: per item, the days sold below its list price, against the yearly limit while it applies; it is information only and never blocks a save.
- **Access.** `useSettingsAccess("rewards")`, the rule of `roles`, for drafting and editing, and `rewardApproval` for Duyệt; everyone else reads the catalogue with `settings.rewards.readOnly.role` or `.scope`. The demo shows its sample catalogue read-only with `settings.rewards.demo` and no discount days.

## Who may write what

Every settings page asks `useSettingsAccess(area, storeId)` (`settingsAccess` in `src/settings/access.ts`) before it offers a control. A member who may write gets the fields and the save bar. Everyone else gets `ReadOnlyNotice` (`src/settings/read-only-notice.tsx`: a note with the reason's message and the reason in `data-reason`) and no control that changes anything: no enabled field, no save bar and no add, publish, retire or delete button. Controls that only read stay: the year on Ngày lễ, the scope or store select of the Dữ liệu nhập tay tabs, the searches of Giá vốn and Nhóm của món, the history toggles, the cost template, "Xem nội dung" on Pháp lý and the device's CSV dialect on Ngưỡng báo cáo. The database decides regardless (row-level security, the column grants, the opening-hours guard and the checks), so a page that offered too much would still be refused.

|---|---|---|---|

Two results follow the design and are recorded so nobody reads them as leaks:

- **A store-limited manager may run the catch-up for the whole tenant.** `refresh_my_analytics` checks the caller's role in the tenant (`app.has_tenant_role`), not the store scope, as [security.md, 5.3](security.md#53-rls-summary-matrix) allows managers. It only recomputes the aggregates from the synced facts, at most 92 days per call, and answers with the number of rows it refreshed; it changes no setting and returns no figure.
- **A store-limited manager who gives their store the code of a store they cannot see gets `23505`.** The code check of `app.stamp_store_profile` is `security definer` and compares the code, trimmed and upper-cased, with every store of the tenant under a lock per tenant; there is no unique index, because two POS accounts may share a code ([schema.md, triggers and helpers](schema.md#triggers-and-helpers)). The refusal tells that manager only that some store of the tenant already uses the code.

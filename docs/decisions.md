# Architecture decisions

Short records of the decisions that shape this system, so that anyone reusing it for another shop knows what was chosen and why. Newest at the bottom.

## ADR-001 — Static frontend on GitHub Pages, data and auth in Supabase, scheduled compute in GitHub Actions

Date 2026-11-07 · Status accepted

The owner wants no servers to run and no manual deployment. GitHub Pages hosts the web app and redeploys on every push. Supabase (free tier) provides Postgres, email/password auth and row-level security so revenue data is never public, plus Edge Functions for the few always-on endpoints that Zalo integrations need. GitHub Actions runs the POS sync on a cron and applies database migrations. The only manual step is creating the Supabase project once and pasting three secrets into GitHub.

Consequence: GitHub Pages on a free account requires a public repository, so the repository holds code only — no data exports, snapshots, identifiers or credentials. Shop-specific notes live in the gitignored `docs/private/`.

## ADR-002 — TypeScript everywhere

Date 2026-11-07 · Status accepted

Frontend, sync jobs and tooling share one language and one toolchain (pnpm workspaces, Biome, Vitest). Database logic is SQL in Supabase migrations with pgTAP tests.

## ADR-003 — No paid AI API; the strategy runs under the owner's own assistant subscription

Date 2026-11-07 · Status accepted

A personal assistant subscription cannot be used by a server. The platform therefore prepares an AI data pack (aggregates only) and stores the resulting plans; the reasoning happens in the owner's own assistant, either through a `/strategy` command run locally or on a schedule, or by pasting an exported data pack into a chat. The strategy prompt ships inside the data pack, and any assistant-specific wrapper lives in the owner's personal configuration, outside this repository. If an API key is ever added, the data pack and prompt stay the same.

## ADR-004 — Canonical POS-agnostic schema behind a connector interface

Date 2026-11-07 · Status accepted

Every POS-specific detail stays inside a connector package (`packages/connector-ipos` first). Connectors normalise into one canonical model: tenants, POS accounts, stores, master data, invoices, invoice lines, payments, shifts. POS ids are kept as `external_id` columns and the original payload in `raw jsonb`, so nothing is lost and anything can be re-derived. Adding another POS means implementing the connector interface, not changing the schema or the reports.

## ADR-005 — Multi-tenant from day one

Date 2026-11-07 · Status accepted

Even with one owner and two stores today, every table carries `tenant_id`, access is granted through `tenant_members` (owner, manager, staff, viewer, optional store scope) and enforced by RLS. A second owner, a second POS account or a third store is a row, not a code change.

## ADR-006 — Credentials never in the database or the repository

Date 2026-11-07 · Status accepted · amended 2026-11-08 for the Edge Function runner

POS credentials (`POS_ACCOUNTS_JSON`, `IPOS_APP_KEY`) live in GitHub Actions secrets, in the Edge Function secrets of `sync-incremental`, and in the owner's local `.env`. The database stores only account metadata, external ids and a service-role-only token cache. The scheduled calls to the Edge Function carry single-use tickets the database issues (ADR-028), so no API key or other credential is kept in the database or in Vault for them. Zalo app secrets will live in Supabase Edge Function secrets.

## ADR-007 — Business day and money conventions

Date 2026-11-07 · Status accepted

Timestamps are stored as `timestamptz`; `business_date` is computed by the sync in the store's timezone (Asia/Ho_Chi_Minh for the first tenant, fixed offset, no DST). Amounts are `numeric(14,2)` in the tenant's currency so the schema also fits currencies with decimals.

## ADR-008 — Local development on a Dockerised Supabase stack

Date 2026-11-07 · Status accepted

`pnpm db:start` runs the full Supabase stack locally (Postgres 17, Auth, PostgREST, Studio). Migrations, RLS and pgTAP tests are developed and verified locally and in CI before any cloud project exists. The seed creates a synthetic demo tenant and a dev login so the web app works offline from the first day.

## ADR-009 — Connector tests use synthetic fixtures; live checks are opt-in

Date 2026-11-07 · Status accepted

Unit tests inject a fake `fetch` with generated fixtures. A live smoke test runs only with `LIVE=1` and local credentials and prints counts and timings only. Recorded real responses are never committed because the repository is public.

## ADR-010 — Analytics aggregates are job-refreshed tables with RLS, not materialised views

Date 2026-11-07 · Status accepted

Postgres does not apply row-level security to materialised views, and a `security_invoker` view over one needs the caller to hold SELECT on it, so tenant filtering would rest on view predicates alone. Aggregates (daily sales, hour × weekday, item sales, payments, shifts, basket pairs, …) are therefore ordinary tables carrying `tenant_id` and `store_id`, refreshed by the nightly and incremental jobs, protected by the same RLS policies as the fact tables and covered by the same two-tenant test matrix. Recent days are served by plain views over the fact tables so "today" is fresh after every incremental run.

## ADR-011 — Early manager value: first live screen before the full sync engine

Date 2026-11-07 · Status accepted

Three independently proposed roadmaps were judged; the ordering that puts a real report on the owner's phone earliest scored best. Sequence: cloud project live with one recent month loaded through the generic onboarding path → web foundation with a "Hôm nay" screen reading real data (badge "chưa đối soát" until reconciliation exists) → sync engine with reconciliation, void detection, schedules and the full backfill → analytics layer. The owner can swap the web and sync phases if unattended data matters more; both depend only on the cloud project.

## ADR-012 — Connector contract with capability flags, proven by a mock connector and a conformance suite

Date 2026-11-07 · Status accepted

`PosConnector` declares capabilities (lines, modifiers, payments, shifts, adjustments, control totals, customers, guest count, costs). A seeded mock connector shaped like the real data passes a conformance suite before the iPOS adapter is written against the interface, so the "generic" contract does not inherit iPOS's shape. A CSV import connector is added later as the second real implementation for shops whose POS has no API. Reports hide sections a POS cannot feed instead of failing.

## ADR-013 — Least-privilege identities for the strategy path

Date 2026-11-07 · Status accepted

`fnb publish-plan` and the optional cloud routine sign in as a dedicated tenant member with the `publisher` role (read aggregates, insert plans, nothing else) using credentials from a local gitignored `.env` or the routine's environment. The manager's login and the service-role key never leave their places (the browser session and GitHub Actions respectively).

Amended 2026-11-20 with phase 11b (#169, #170, #177). The publisher reads only tenants, stores, holidays and the calendar (and the global notification catalogues); it reads no aggregate, sale, pack or plan, holds no `INSERT` on `strategy_reports` and publishes only through `publish_strategy_plan`. Packs are built by a data member: in the browser by the signed-in owner or manager, or by `fnb datapack` acting as one through its own database connection. `fnb publish-plan` signs in with the publishable key and the publisher's e-mail and password only, and refuses a login that can read `tenant_members`.

## ADR-014 — Realistic acceptance gates

Date 2026-11-07 · Status accepted

Backfill is accepted at ≥ 99 % of store-days reconciled with every exception explained privately; one month syncs in under 5 minutes within a stated API-call budget; the E2E suite must be green with zero flakes over five consecutive runs on a staging Supabase project seeded with mock data; v1.0 requires a 7-day parallel verification against Fabi reports A01, B07 and C02 per store; backups are encrypted and restore-tested. The nightly digest runs as the last step of the final incremental sync of the day so it never misses the evening peak.

## ADR-015 — Secret and identifier scanning uses generic rules in CI

Date 2026-11-07 · Status accepted

CI cannot see the gitignored private identifier list, so the scanner uses generic patterns (32-hex app keys, Supabase and JWT key shapes, e-mail addresses, UUIDs) with an allow-list for documented examples and tests; the private list is checked locally before the first commit of each phase.

## ADR-016 — Loyalty: our ledger is the system of record; iPOS CRM is an optional rail

Date 2026-11-07 · Status accepted (rail choice pending the iPOS CRM quote)

Research (fact-checked against iPOS's and Zalo's own documentation) shows that iPOS exposes no public write API; the only documented ways an identity or a coupon reaches a Fabi invoice are the iPOS CRM module (cashier attaches a member by phone or check-in code, e-voucher codes typed at the POS, and a restaurant-hosted voucher-validation callback). Points, stamps, coupons and customers therefore live in our Supabase ledger, computed from the synced invoice stream, which remains the proof of purchase. iPOS CRM is used only for what it uniquely does at the till — if its quote is acceptable. Without it, the same ledger works with staff-verified check-ins, receipt-code claims and Fabi payment-discount entries. The rail is configuration per store; the ledger and both Mini Apps do not change.

## ADR-017 — One Zalo App and one verified Official Account per brand; two Mini Apps per brand

Date 2026-11-07 · Status accepted

Zalo's single-brand-per-app rule and OA-based Mini App verification lead to: one Zalo App (developers.zalo.me) per brand holding that brand's Staff Mini App (Internal classification, distributed by QR and deep link) and Customer Mini App (public), one verified OA per brand on the Tăng trưởng package (required for any Open API use), and one ZBS account for the legal entity. All Zalo identifiers and secrets are per-brand configuration rows and Vault/CI secrets, never code.

## ADR-018 — Messaging economics: in-app first, free OA window second, paid templates last

Date 2026-11-07 · Status accepted

Confirmations and balances are shown in the Mini App; consultation messages are sent free inside the 48-hour interaction window; paid ZBS template messages (raised in 2026 to roughly 300–400 ₫ each) are reserved for issued vouchers, expiry reminders and win-back campaigns, within Zalo's per-user caps; staff alerts go through the free Zalo Bot API and the OA group included in the package. An outbox with per-channel quotas and fallback order enforces this.

## ADR-019 — Cross-border hosting of personal data: dossier or exemption before launch

Date 2026-11-07 · Status open (reframed after the legal deep dive)

An early research note said Zalo's Mini App agreement requires Vietnam-resident storage of Zalo-derived data; no primary source has confirmed that clause. The verified duty is in the personal-data law in force since 1 January 2026: hosting customer data on Supabase (Singapore) and GitHub is a cross-border transfer that normally needs a transfer impact dossier filed within 60 days of the first transfer — unless the business is a household business or micro-enterprise (exempt) or a small enterprise (may defer to 2030), and provided no sensitive data is processed and fewer than 100,000 data subjects are reached. The owner confirms each brand's legal form in week 1; the choice (file or record the exemption) is gate G3 and must be made before Track C goes public. Zalo-derived data stays minimal (Zalo id, display name, phone), analytics events stay aggregate, and the database remains portable to a Vietnam-hosted Postgres if a requirement ever appears.

## ADR-020 — Two runners, one sync engine: incremental on Supabase, heavy jobs on GitHub Actions

Date 2026-11-07 · Status accepted

GitHub's Actions terms exclude use "as part of a serverless application" and activity unrelated to building and publishing the project, scheduled runs are routinely 20–40 minutes late and are disabled after 60 days without repository activity. A twice-hourly POS sync on Actions is therefore both a terms grey area and an unreliable freshness promise. The sync engine is built on supabase-js and runtime-agnostic connectors, with two runners: an Edge Function invoked by `pg_cron` every 30 minutes per store during opening hours (last 3 business days, change detection first, a CPU/time guard that hands oversized windows to the nightly job), and a Node runner on GitHub Actions for the nightly job, backfills, backups and the owner's CLI. Actions schedules use off-peak minutes and the cron timezone field, a dead-man's-switch alert fires when the last successful run is older than 90 minutes during opening hours, and a keep-alive guards the 60-day rule. A small server is the documented fallback for every scheduled job.

## ADR-021 — Legal compliance is built into the schema, the apps and the campaign engine

Date 2026-11-07 · Status accepted

Vietnam's personal-data law (in force since 1 January 2026, with its 2025 and 2026 decrees), the promotions decree (as amended in 2024), the 2026 e-invoice decree and the anti-spam decree set duties the platform must satisfy by construction: a per-purpose consent ledger with evidence (loyalty, marketing, staff operations) and a working opt-out; data-subject requests tracked against the 2-working-day first response and 20/30-day completion deadlines, with cascading deletion; a 72-hour breach notification runbook; the cross-border dossier or exemption decision (ADR-019); a programme record (name, period, reward budget) that drives the Sở Công Thương notification check (required for customer loyalty programmes unless the total gift value stays under 100 M₫ — the 2024 amendment removed notification for ordinary discounts and vouchers, not for loyalty programmes); the 50 % discount cap and the 120 discount-days per item per year counter on coupons; no cash-like rewards; every redemption modelled as a Fabi discount or 0-price promotional line so the cash-register e-invoice shows it; channel policies with allowed hours, daily caps, advertising labels, opt-out text and consent purpose; an outbound-message log kept at least one year. The owner's entity-specific choices (legal form, filings) are confirmed by a legal read before Track C goes public.

## ADR-022 — Zalo policy rules are acceptance criteria

Date 2026-11-07 · Status accepted

Zalo's Mini App review policy and OA rules are treated as build requirements rather than launch risks: no outbound links from a Mini App except embedded Privacy and Terms (so no links to the web dashboard; Terms and Privacy are in-app popups titled for the Mini App and naming the legal entity); no prices shown without the Checkout SDK (menu highlights say "Xem tại quầy" until ordering is scoped); no permission prompt at launch and a usable "từ chối" path; personal-data permissions requested with reason text and screenshots at the first Testing submission (test users bypass approvals and prove nothing); names with an owner-identifying prefix or suffix and no generic nouns, "App", "Mini App" or "Zalo"; logos without QR codes or phone numbers on a solid background; performance gates (LCP < 2.5 s, page load < 1.5 s, bundle and per-file budgets) enforced in CI; ≤ 4 bottom tabs, one primary action per screen, 44 × 44 pt targets; `app-config.json` generated per tenant so one codebase ships one Mini App per brand; consultation messages through the API only within 7 days of the user's last interaction; broadcasts manual-only within their caps and hours; template messages only to users who transacted; Mini Apps kept above 10 visits per month and OAs active toward followers within 180 days, monitored by alert rules.

## ADR-023 — Supabase and GitHub operating conventions

Date 2026-11-07 · Status accepted

New Supabase key scheme from the start (`SUPABASE_SECRET_KEY` for jobs and functions, `SUPABASE_PUBLISHABLE_KEY` as the public web variable; legacy JWT keys disabled once everything works); `SUPABASE_DB_PASSWORD`, `SUPABASE_ACCESS_TOKEN` and `SUPABASE_PROJECT_ID` for migrations; the Supabase CLI pinned in CI; `db diff --strict-coverage` and generated-types drift checks in CI; custom SMTP (or the send-email hook) configured before inviting users because the built-in mailer allows two emails per hour; weekly encrypted `supabase db dump` backups through the session pooler from the first day real data exists, stored outside the public repository, with a guard against `db reset --linked` and a restore drill; egress budgeted (backups, exports); Data API pagination with stable ordering under the 1,000-row default; all audit and sync logs in our own tables (platform logs are kept one day on the free tier); email sent through an HTTPS provider because Edge Functions block SMTP ports; `fnb doctor` reports database size, disk, egress, pause risk and the Pro upgrade trigger (~400 MB, a second owner, or mandatory daily backups). GitHub: credential fields of `POS_ACCOUNTS_JSON` are masked at job start (or stored one secret per account), job summaries carry no identifiers, `.nojekyll` is present, the SPA uses hash routing with the PKCE auth flow unless the 404.html approach is chosen, a `version.json` prompt handles the fixed 10-minute Pages cache, and the absence of CSP/HSTS on Pages is accepted with Cloudflare Pages as the drop-in fallback.

## ADR-024 — iPOS CRM is already present; the loyalty ledger stays independent of it

Date 2026-11-07 · Status accepted (rail choice at gate G2)

The hands-on review of the Fabi CMS found iPOS CRM initialised for both brands at no charge, with a published price list (one-time voucher codes 100 ₫ each, Zalo messages through CRM 55 ₫ each, optional setup 4,000,000 ₫, a restaurant-hosted voucher-validation callback that iPOS would build for 1,000,000 ₫), and that the tea brand's CRM tiers belong to the franchise brand's CRM company and may be shared with other franchisees. Points, stamps, coupons and customers therefore live only in our ledger (ADR-016); CRM is used, if at all, for attaching a member at the till and consuming voucher codes, never for tiers or points that other stores could change. Receipt claims are keyed on store + business date + bill number because bill numbers reset daily at one shop and yearly at the other. The owner confirms the shared-tier question and current rates before gate G2.

## ADR-025 — Connectors use documented read endpoints only; vendor security observations are handled privately

Date 2026-11-07 · Status accepted

During the read-only CMS review, some CMS forwarding endpoints returned credentials of vendor service accounts and another brand's configuration in plain text. The connector calls only the documented posapi read endpoints used by the sync, never the CMS forwarding or CRM endpoints; nothing returned by such endpoints is stored, logged or reused; the observations are recorded only in the private notes, and the owner decides whether to report them to iPOS (responsible disclosure recommended).

## ADR-026 — Standard KPI methods in the metric registry

Date 2026-11-07 · Status accepted

Reports, the data pack, digests and KPI follow-up share one registry of about forty metrics with id, bilingual label, unit, formula, grain, direction, source and report mapping. Methods adopted: Kasavana–Smith menu engineering per item-type role and store over a rolling 28-day window with configurable thresholds and a "provisional — no cost" state until item costs exist; average ticket decomposed into items per ticket × average item price; same-weekday 8-week median baselines excluding holidays and Tết; seasonal-naïve and weekday-profile benchmark forecasts with tracked error; promotion lift as difference-in-differences against a chosen comparator, always net of discount cost; cash variance with absolute, relative and z-score thresholds; void, edit and removed-line rates ranked by z-score within a store; RevPASH and sales per opening hour where seats are known; loyalty economics with points valued at issue, liability net of expected breakage (20 % default until six months of expiry data) and deferred revenue released with redemptions; customer metrics (repeat rate, visit frequency, cohort retention, RFM, lifetime value) computed on identified customers with the capture rate reported alongside. Vietnam benchmarks are stored as dated "context" entries separate from tenant metrics.

## ADR-027 — Sale payloads live in one compressed document per store-day

Date 2026-11-08 · Status accepted

The full backfill of both shops put the database at about 850 MB against the 300 MB ceiling of phase 7, two thirds of it `raw jsonb` on invoices, lines and tenders: a line payload is about 3 kB and a row under 2 kB is never compressed, so the storage rule for lines would have saved little. Dropping payloads would break ADR-004 ("nothing is lost"). Instead the sync writes null to those three `raw` columns and keeps every sale's payloads in `sale_payloads`, one lz4-compressed JSON-lines document per store and business date, with line and tender payloads stripped of the fields equal to their invoice's. Within a day the field names and many values repeat, so the documents compress about ten times and the same history fits under the ceiling. A future column is back-filled by reading the document of the sale's store-day.

## ADR-028 — Scheduled calls to the incremental Edge Function carry a single-use ticket, not an API key

Date 2026-11-08 · Status accepted

`pg_cron` calls `sync-incremental` through `pg_net`, so whatever authorises the call is stored in the database and, until the request leaves, sits in `net.http_request_queue`. Supabase supports three ways to authorise it. Its scheduling guide ([supabase.com/docs/guides/functions/schedule-functions](https://supabase.com/docs/guides/functions/schedule-functions)) sends the project's secret key on the `apikey` header and has the function accept only that key; a secret key bypasses row-level security on the whole Data API, it would live in Vault, and the same guide warns that any role able to log in can read it from the queue while the request waits. The publishable key is public by design, so it authorises nothing: anyone with the web bundle could make the function call the POS. The third way is `verify_jwt = false` with the function checking the caller itself, and this is the one used, with the least privilege it allows: the scheduler issues one random ticket per due store in `app.incremental_sync_tickets`, with a 10-minute life, and the request carries only that id; the function claims it, deleting it, through its own database connection before it does anything, and answers 401 to an unknown, used or expired ticket. No credential for the schedule exists anywhere. A ticket read from the queue or a log can at most start one sync of one store, once, within minutes. A caller without a valid ticket costs one invocation and one indexed delete, made over the worker's single shared claim connection, so anonymous traffic never opens database connections of its own and cannot exhaust the Free plan's small connection limit; while 32 claims wait on that connection the function answers 429 without touching the database. Only a claimed ticket opens the run's own connections. Signing tickets with a key held in Vault and in a function secret would turn bad tickets away before any query, but it would put a credential back into the schedule, which this decision avoids. Manual runs use `app.issue_incremental_sync_ticket`.

The same function connects to Postgres with postgres.js over the injected `SUPABASE_DB_URL`, the direct connection, always over TLS for a host that is not local (a URL that would allow plaintext is refused), and reuses `PostgresSyncRepository` rather than an RPC-backed repository: the session advisory lock that serialises a store's runs is then the same for the Edge Function, the nightly job and the CLI, and the Edge Function gives way after 15 seconds instead of queueing behind a backfill.

## ADR-029 — Report numbers come from SQL; the demo runs a parity-tested TypeScript port

Date 2026-11-08 · Status accepted

The periodic reports (phase 9) need the same numbers in three places: the live web app, the demo that runs in the browser with no backend, and later the data pack, KPI follow-up and digests. Every sum, ratio, median and forecast of a report is computed in SQL, in `security invoker` functions that the browser calls through `supabase.rpc()` as the signed-in member, so row-level security and the single production source stay as `docs/metrics.md` and `docs/schema.md` describe them; TypeScript only adds what sits on top of those rows (changes, the exact decomposition, like-for-like selection, rankings, statuses and sentence drivers), in pure card models of `@fnb/reports` that every consumer shares. The demo cannot run SQL: PGlite in the browser would cost 4–5 MB of WebAssembly. Instead `@fnb/demo-analytics` ports exactly those functions to TypeScript, over days generated from the mock connector and aggregated as the nightly refresh does, behind the same `AnalyticsSource` interface, and a parity suite applies the real migrations in PGlite (and, in CI, on the real stack), loads the same days and compares every row and value, so a change to a function that is not mirrored in the port fails the build. The cost is a second implementation of each function, paid once per function and kept honest by the parity suite rather than by review.

## ADR-030 — One Postgres outbox; every send decision in SQL at claim time; policies as rows with legal floors; alerts as episodes

Date 2026-11-20 · Status accepted

Digests and alerts reach owners and managers through several channels (Zalo Bot, e-mail, later Telegram and a signed webhook) with rules that differ by channel and message class: sending hours, daily and monthly caps, consent, labels for advertising. Decision: every message is one row of `outbound_messages`, inserted only through `app.enqueue_message`, and the decision to send, hold or cancel is taken in SQL when a dispatcher claims the row (`app.message_decision`), not when it is queued, so a policy or consent change applies to messages already waiting. Policies are rows of `channel_policies` per channel kind and message class, global or per tenant, and the legal floors (consent for every member destination, the advertising window, cap, label and opt-out of Decree 91/2020) are CHECK constraints that bind every writer, the service role and the browser included, so no override can store a policy below the floor. A provider that honours an idempotency key (Resend, the signed webhook) is retried with the same key after a crash between send and record, so it delivers exactly once; any other provider's row becomes `uncertain`, never resent automatically, and a person resends it (`resend_message`, `fnb notify resend`) as a new row that points at the original, numbered `:resend:<n>` under an advisory lock. Alerts are episodes (`alert_events`): one open row per dedupe key with occurrences, a cool-down, reminders, folding under a root cause and a resolution notice, so a repeated reading never repeats the message. Not chosen: a queue service outside Postgres (another system to run on the free plan, and the decision would need the policy rows anyway); deciding at enqueue time (a consent withdrawn after queueing would not stop the message); automatic resends of `uncertain` rows (a duplicate digest is worse than a late one).

## ADR-031 — The digest is the Ngày report as its recipient sees it, sent once its stores have settled the day or at 06:30, corrected at most once

Date 2026-11-20 · Status accepted

The owner reads the morning digest instead of opening the app, so its figures must be the ones Ngày shows. Decision: the digest is built from the same report functions as Ngày (ADR-029), called as the member who receives it so row-level security and the member's store scope apply, one digest per tenant, business date and scope (members with the same stores share it). It is built when every store of its scope has settled the day (its last sync after closing plus the grace minutes) or at the tenant's `deadline_local` (06:30 by default), whichever comes first, instead of as the last step of the final incremental window, which ADR-014 and the roadmap's phase 12 text described before (amended by this record). After the nightly reconciliation the digest of the last two business dates is rebuilt (`fnb digest --revise`; its SQL half, `app.digests_to_revise` and `app.revise_digest`, is still to be built, see docs/test-gaps.md): an unchanged fingerprint changes nothing, a digest whose messages are still waiting is replaced silently, and a shown figure that changed or a new attention line sends one `digest_correction` per destination, never a second one. Not chosen: sending at a fixed hour regardless of the data (a digest built on an unsynced day would need a correction most mornings); sending a correction for every change (a stream of updates trains the owner to ignore them).

## ADR-032 — Two dispatchers and a database-free failure path

Date 2026-11-20 · Status accepted

GitHub's scheduled workflows often start late or not at all, and the free Supabase project pauses after a week without activity. Decision: two dispatchers run the same cycle (`runNotifyCycle` of `@fnb/notify`). The `notify` Edge Function is woken by the `pg_cron` job `notify` (`app.enable_notify`, every 5 minutes, off until the owner enables it) through single-use tickets as ADR-028 describes for the incremental sync, works within the Free-plan budget (90 s, 4 digests, 30 sends, at most 3 chained continuations) and claims rows with a lease so two dispatchers never send the same message. The CLI on GitHub Actions (`fnb notify tick`) runs as a fallback and skips itself while the Supabase dispatcher is healthy. A scheduled workflow that fails is reported by a `workflow_run` listener through `fnb notify job-failed`; when the database cannot be reached or nothing was recorded, `scripts/notify-fallback.mjs` sends one fixed text per target from the `NOTIFY_FALLBACK_TARGETS` secret with no database at all, so a paused project still reaches the owner. Not chosen: Actions only (late schedules delay alerts by hours); the Edge Function only (a paused project or a broken deploy would go unnoticed); a third-party uptime service (another account with the owner's data).

## ADR-033 — Credentials by reference, consent at the member's own act, owner-only rule overrides, internal messages are not advertising

Date 2026-11-20 · Status accepted

A destination row names the environment variable that holds its credential (`secret_name`, `NOTIFY_` with the kind's prefix), never its value; dispatchers report which names they hold, and a message whose secret no runtime has reported for 48 hours is cancelled as `no_dispatcher_secret` instead of waiting. The member's `notifications` consent is recorded only at their own act: the "ĐỒNG Ý" reply to the bot's notice, the e-mail code, or the web link of their own login address (`start_channel_link`, method `web_session`); an owner or manager never records it for someone else, and `stop_my_notifications` or "DỪNG" withdraws it. The browser never sees an address, chat id, secret name or destination configuration (column grants and function results), and webhooks are added from the command line only. Alert rule and policy overrides are written by owners with every store only, because the rules include signals that watch the managers; managers read them and mute rules on their own destinations. A member who leaves loses their destinations with the membership (cascade), and their messages keep only count-only parameters. Digests and operational alerts to the business's own owners and managers are internal operational messages, not advertising: they need the member's consent and respect the channel's hours, but the advertising label, cap and opt-out text of Decree 91/2020 apply only to the advertising class, which stays disabled until the customer phases. This is the project's reading for building, not legal advice; the owner's legal review stays an owner item (#15).

## ADR-034 — One token source in the DTCG format; accessible primitives in the shadcn pattern; WCAG 2.2 AA

Date 2026-11-14 · Status accepted

The web app defined its colours in five places (the light, dark and print blocks of `styles.css`, and the screen-fallback and print palettes of the chart theme), and the copies had already drifted: the chart fallback's second series colour differed from the CSS one. Control styles were copied as class strings (the primary button four times, the text input three times), and the store picker, the language switch and the folded controls each implemented their own open, close, focus and keyboard behaviour. The Zalo Mini Apps of track B will need the same brand in zmp-ui. The owner asked for a standard that keeps this easy to maintain. Decision: every colour, font stack and print size is a token in the Design Tokens Format Module 2025.10 of the W3C Design Tokens Community Group, kept in `packages/design-tokens`; Style Dictionary 5 generates from it the CSS variables with the Tailwind 4 `@theme inline` mapping and a typed palette for ECharts, and later the zmp-ui theme, and the generated files are committed and checked for staleness in CI like the Edge Function's import map. ## ADR-037 — Mini App sessions are minted through the Auth admin API (generate_link + verify)

Date 2026-11-18 · Status accepted · amended 2026-11-18

A Mini App runs inside Zalo with no password, no cookie and no web storage, and it must reach the same Data API under the same row-level security as the web app. Zalo gives the Mini App an access token for its own Zalo App; Supabase Auth has no Zalo provider. Decision: the Edge Function `zalo-session` (#205) confirms the access token with Zalo's Graph and the app-secret proof (HMAC-SHA256 of the token keyed with the brand's App secret), finds the member bound to that Zalo identity in `zalo_identities` (bound once with a one-time code that `fnb zalo bind` issues), and mints a genuine Supabase session for that member's existing login through the Auth admin API with the secret key: `POST /auth/v1/admin/generate_link` with `type: magiclink` and the login's e-mail gives a hashed token, and `POST /auth/v1/verify` with that token gives the access and refresh tokens. No e-mail is sent and nothing in the repository signs a token. Every access token Auth issues, the web app's included, carries the claim `memberships` (`[{tenant_id, role, store_ids}]`, `store_ids` null for every store) from the access-token hook `app.custom_access_token_claims`, so a Mini App shows the member's role and stores without a query, while row-level security keeps reading `tenant_members`.

Consequences, from Supabase Auth's own behaviour, which the build relies on and the cloud project confirms in #210: the login's last sign-in time moves at every Mini App sign-in, so it no longer tells when the member last used the web app; generating the link replaces any magic-link or recovery token the login was waiting on, so a password-reset link sent just before a Mini App sign-in stops working and must be requested again; `/verify` is limited per IP address (30 verifications per 5 minutes, `token_verifications` in `supabase/config.toml`), and every Mini App sign-in reaches it from the function's own address, so a burst above that limit is refused until the limit is raised on the cloud project; and a bound login without an e-mail cannot get a session (`session_unavailable`). The Mini App's session and a web session are independent sessions of the same login, each refreshed on its own.

Not chosen: a separate Auth user per Zalo identity without e-mail or password, the issue's first sketch, because a second login per member would split roles, store scopes and attribution between two users; a token signed by hand with the project's JWT secret, which would put that secret in a function and bypass Auth's sessions and refresh; and Auth's anonymous sign-in or an external OIDC provider, since Zalo's access token is not an OIDC token. Applied in [api.md](api.md) (sections 2 and 5), [security.md](security.md) (sections 4.3 and 5.1), [schema.md](schema.md) ("Sign-in functions and the access-token hook") and [architecture.md](architecture.md) (sections 6.6 and 11).

Amended 2026-11-18 with the staff pairing of phase 14a (#213): staff on the roster have no login of their own until they pair, and the minting above needs one. Decision: at a person's first pairing, once the database has accepted the code and the notice (`app.zalo_pair` answers `login_needed`), `zalo-session` creates one Auth user for the roster row through the Auth admin API, `POST /auth/v1/admin/users` with `email_confirm: true` and no password, at the address `staff-<random uuid>@zalo-staff.invalid`; the database takes it only when it belongs to nobody yet (`app.staff_login_is_fresh`) and stores it on the row, which keeps it for every later pairing, in another brand's app or after a reactivation; the function deletes the user again when the pairing did not use it. Sessions are then minted for it as above. `.invalid` is reserved (RFC 2606) and resolves nowhere, so the address names nobody, receives no mail and cannot be taken over, and with no password the login's only way in is a Mini App session for its bound Zalo identity. Consequences: these logins never sign in to the web app; the web app knows the person by the roster's display name, never by this address; and a failed clean-up leaves a login with no password, membership or identity, which the function logs without naming. This is one login per person, not the rejected login per Zalo identity: the person's identities in each brand's app all point to it, so roles, store scope and attribution stay on one user. Applied in [schema.md](schema.md) ("Staff roster, consent and pairing (phase 14a)") and [security.md](security.md) (sections 4.3 and 5.1).

## ADR-046 — Balances never go negative: adjustments are floored, clawbacks are capped at what is left, pending earns neither expire nor count

Date 2026-11-22 · Status accepted (delegated) · closes G-102 and G-43

Decision: (1) a manual adjustment that would take a stamp or point balance below zero is refused (22023). (2) A clawback of an earn (a void, a reversal) takes back at most the member's current balance of that kind; the part that cannot be taken is a write-off the programme absorbs, written on the clawback row as "short by n" and counted in the nightly counts. A clawback of an earn that already expired takes back only what is left of it, normally nothing. (3) A pending earn never expires while pending: its expiry clock starts when it is confirmed. (4) The wallet shows the ledger balance, which is now never negative; the `greatest(0, …)` in the wallet stays as a safety net (so the choice of G-43, show 0, is the rule and now agrees with the ledger).

Why: stamp and star schemes in retail and F&B carry no member debt; a balance below zero cannot be explained at the till, and netting a debt against the next earn punishes a customer who disputed a void. The loss is bounded by the voided earn itself.

Not chosen: negative balances (the airline model needs a debt rule and a collections process), netting against the next earn, showing the customer a negative figure.

Build: the floor in `app.loyalty_apply_adjustment`, the cap in the clawback writers, pending earns skipped in `app.loyalty_expire`, pgTAP for each, then the second half of G-15 (generated sequences through the app functions).

Built 2026-11-23 (migrations `20261123120000_loyalty_adjustment_floor`, `130000_pending_earn_expiry_clock`, `140000_loyalty_clawback_cap`). (1) `app.loyalty_apply_adjustment` refuses with 22023, and writes nothing, a negative part larger than the spendable balance of its kind; a positive part is never refused. (2) Every clawback goes through one writer, `app.loyalty_write_clawback` (used by `app.loyalty_clawback` and `app.bill_reverse`): a pending earn is taken back whole, a confirmed earn up to the member's spendable balance of each kind, an earn that already expired nothing; the part not taken is written on the row's reason as "short by n stamp(s) and n point(s)" (there is no notes column) and counted in the nightly answer as `written_off_stamps` and `written_off_points`. A clawback while a hold is open can write off points that a later release returns, which follows the decision literally. (3) A pending earn never expires: `app.loyalty_expiring_points` and `app.loyalty_expire` skip unconfirmed earns, and the confirm step starts the clock (the ledger is append-only, so the expiry is written on the confirm row and the earn's stamps get new expiries). (4) The wallet keeps `greatest(0, ...)` on stamps and now on points. ## ADR-047 — A credit is valid through the end of its anniversary day and is spendable until that instant, not until the nightly row

Date 2026-11-22 · Status accepted (delegated) · closes the two expiry questions

Decision: a credit's last day is the local date of the sale (tenant time zone) plus the programme's months, clamped to the last day of a shorter month as built (31 August plus six months is 28 February). It is valid through 23:59:59 of that date: `expires_at` is the local midnight that ends it. A credit is shown in the balance and can be spent while the moment is before `expires_at`. The nightly `app.loyalty_expire` only writes the ledger row afterwards, at its next run; between midnight and that run the credit is already unspendable and out of the wallet, whatever rows exist. Credits that have not expired yet are moved to the end of their anniversary day, later by under 24 hours, so no member loses anything. The Mini App states a date ("valid through 19 Nov 2027"), never a time.

Why: loyalty terms and vouchers are dated, not timed, and a time of day that no receipt shows leads to disputes at the till; end of day is the retail convention and what Vietnamese vouchers state. Spendability must follow the instant, not a job's timing, or the window depends on when the cron ran.

Not chosen: the sale's moment (the current build: invisible to the customer, and "the same day" means different hours for different credits), expiry at the nightly run.

Build: `app.loyalty_earn` sets the end-of-day `expires_at`, a data migration moves the unexpired credits, `pgtap:231` changes its three same-day credits (02:00, 09:00 and 23:30) to expire together and gains the midnight-to-run window, and the wallet and the Mini App read the instant.

Built 2026-11-23 (migrations `20261123150000_credit_end_of_day_expiry`, `160000_spendable_at_the_instant`, `170000_credit_expiry_end_of_day_data`). `app.loyalty_credit_expires_at` gives the local midnight that ends the local date of the sale plus the months (clamped); every writer of an expiry uses it (earn, bill earn, welcome stamps, adjustment, both confirm steps), so every date shown is a "valid through" date. `app.loyalty_balance(membership, at)` leaves out credits whose expiry has passed at `at`, whatever expire rows exist (with a null moment it is the plain ledger sum; `public.loyalty_balance` passes `now()`). Points expire first in, first out by aggregate, so a hold or a manual debit between a credit's midnight and the nightly run would be counted against the dead credit; before one is accepted, `app.redeem_coupon` and the negative part of `app.loyalty_apply_adjustment` first run the member's due expiry (`app.loyalty_expire_membership`, also used by `app.loyalty_expire`), so an expire row can appear at the debit's moment instead of at the nightly run and counts in that day's liability flows. The data migration moves each unexpired credit to the end of its day with the append-only trigger disabled inside its own transaction and enabled again before the commit (expiry column only, never earlier, at most 24 hours later; 2 ledger rows and 4 stamps on the local database). The wallet emits `valid_through` and `expires_at` and keeps `expires_on` and `on` with the same last valid day for older Mini App builds; the customer Mini App says "valid through dd/mm/yyyy", never a time, and reloads once if the end passes while the wallet is open.

## ADR-048 — Liability counts confirmed points only, the daily flow covers the closed previous day, breakage cohorts follow the credit

Date 2026-11-22 · Status accepted (delegated) · closes G-103 and G-104

Decision: (G-103) the liability is the confirmed outstanding points times the point value times one minus the breakage rate; a pending earn is not a liability until it is confirmed, so the clawback of a pending earn lowers nothing. (G-104 F1) an expiry is attributed to the month its credit was issued, through the earn row it expires, and only a row without that link falls back to first-in first-out. (G-104 F2) `points_issued`, `points_redeemed` and `deferred_revenue_released_amount` of a run cover the whole previous local business day, from its start to the start of the next, so the 03:23 nightly reports a complete day (the definition of the digest, ADR-031) and a late run still reports that day only.

Why: revenue recognition is done on a closed period and an obligation is counted once, when the credit is earned and confirmed (the IFRS 15 and ASC 606 treatment of loyalty credits); breakage is analysed by vintage, which is the month a credit was issued; half-day aggregates mislead.

Build: a migration for `app.loyalty_liability` and the breakage function, then the labelled KNOWN LIMITATION assertion of `pgtap:236` changes to the new rule; do it before any page reads these columns.

Built 2026-11-23 (migration `20261123090000_liability_flows_and_cohorts`), with two refinements found while building. (1) An `expire` row is one row per member and carries no link to an earn, so F1 is traced the way the row was written, first in first out, which is the fallback this decision named: at the moment of each expiry run the member's credits past their expiry (net of their clawbacks) are lined up oldest expiry first, the spent points took the front of the line, so the expired points are its last ones, and each credit is charged with its share under its issue month. What cannot be traced keeps the old month (the run month less the expiry period); the cohorts' expired points always add up to the expiry rows of the ledger. (2) F2 covers all five flow columns of a row (`points_issued`, `points_redeemed`, `points_expired`, `points_clawed_back` and `deferred_revenue_released_amount`), not three: a row that mixed yesterday's issued points with today's expired ones would not add up. The stock columns (members, outstanding points and stamps, the liability) stay those of the moment of the run. Tests: `core:unit/loyalty-liability` (57), `pgtap:236`, `pgtap:238`, `pgtap:65`.

Two changes after an independent review of 2026-11-23: the cohort trace was quadratic (an expiry row per member re-lined the whole history and a correlated subquery scanned all traced rows per expiry row: 10, 20 and 40 members took 1.8, 8 and 34 seconds), so `20261123180000_liability_trace_one_pass` reads each credit once with its effective expiry, confirm moment and clawback and carries each traced part with its run (20 members took 6.4 s, now 0.34 s, identical cohorts on 200 random tenants; `pgtap:245`); and the trace skips unconfirmed pending earns like the writer does (`pgtap:246`, `core:unit/loyalty-liability`, six new cases).

## ADR-050 — An invoice whose amount changes after it earned goes to a manager; the earn is not recomputed by itself

Date 2026-11-24 · Status accepted (the owner delegated the choice: "all other thing you choose for me") · closes the decision of G-44

Decision: when a sync or the nightly re-pull changes the net amount of an invoice that already earned on a POS path and is not voided, the loyalty reconciliation compares what the earn gave with what the programme's rules give for the new amount. When they differ, one item opens in the loyalty queue for the store's managers (path D, reason `earned_invoice_edited`), naming the invoice and its earn; the manager settles it with an ordinary adjustment, which ADR-046 floors at the balance, or closes it with a reason. An item is opened once per invoice. A void stays an automatic clawback (G-03); an amount that changes back to what earned opens nothing.

Why: a difference that a rule cannot settle safely goes to an exception queue for a person, which is how reconciliations are run. An edit after payment is rare, and it is a known cashier-fraud pattern (ring a large bill, let a member claim it, then edit it down), so a person should see each one rather than have the system quietly absorb it. An automatic correcting entry would touch the ADR-046 cap, the expiry order, the liability cohorts (ADR-048) and the replayed ledger model (G-15) for a rare case.

Not chosen: keeping the first amount silently (hides the fraud pattern); an automatic entry for the difference (the ripple above); reversing the earn and earning again on the new amount (with the ADR-046 cap, a member who already spent the points would be credited twice).

Build: the comparison in the reconciliation, the new queue reason, its wording on the web queue page, and state-transition tests (amount down below the stamp minimum, amount up across it, the amount changed back, a voided invoice, a second change of an invoice already queued).

## ADR-052 — The erased-phone memory is a keyed hash with a key per tenant

Date 2026-11-24 · Status accepted (delegated) · closes the decision of G-46

Decision: the memory of erased phones stores an HMAC-SHA-256 of the phone in E.164 form, keyed with 32 random bytes per tenant that live in a table no API role can read and are created at the tenant's first erasure. Two tenants hold different values for one phone. Entries written before this change (a plain SHA-256) still match; an old entry is rewritten in the keyed form the first time its phone is seen again (a synced invoice, a join, a new erasure). What stays: someone with full access to the database can read a key and still test every possible number of that tenant. That is accepted, because the same person can already read every phone of the members who were not erased, while an erased customer's data is gone.

Why: pseudonymisation guidance (ENISA, 2019) treats a plain hash of a phone number as reversible by trying every number, and recommends a keyed hash. A key per tenant keeps one tenant's list from being linked with another's and makes precomputed tables useless, so a copy of the list alone (an export, a log, a support extract) reveals nothing. The key stays inside the database because a restore must bring it back: a key lost in a restore would silently empty the erasure memory, and the POS would bring the erased phones back, which is the worse harm.

Not chosen: Supabase Vault or a function secret (a restore into a new project, the disaster case of `backup.yml`, would lose the key); a slow hash (paid again at every synced invoice); keeping the plain hash.

Build: the key table, `app.phone_hash` per tenant, every reader and writer of `app.erased_phones`, and pgTAP that two tenants hold different values for one phone, that an old entry still blanks a synced phone and is rewritten in the keyed form, and that no API role reads the keys.

## ADR-054 — A data export stays a browser download that no server keeps, and each download is recorded

## ADR-055 — The member frequency uplift compares matched cohorts; no hold-out group

Date 2026-11-24 · Status accepted (delegated) · closes the decision of G-54

Decision: the uplift compares members with identified non-members of the same cohort: the same first-visit month and the same first store (an exact match on both). Each cohort cell's difference in visit frequency is weighted by its number of members; a cell with fewer than 10 customers on either side is left out; with fewer than 10 matched members in all, the uplift stays null. The answer names the comparison `matched_cohorts` and gives the matched sizes. There is no hold-out group. `customer_ltv` waits until item costs cover the stores.

Why: customers who already come often are the ones who join, so the plain gap between members and non-members overstates what the programme does. Matching on tenure and store is the standard low-cost correction (coarsened exact matching). A hold-out would deny the programme to some customers, which a single store cannot explain at the till, and it would leave too few customers to measure anything.

Not chosen: a configured hold-out group; propensity-score matching (too few identified customers for a model to be stable).

Note: on 2026-11-22 the real tenant's 30 days held no invoice with a phone or customer id, so the uplift will read null there until the till records customers.

Build: the cohort comparison in `customer_metrics`, its documentation in metrics.md, the web wording of the comparison, and a hand-calculated pgTAP case beside `pgtap:163` with two cohorts of different tenure.

## ADR-057 — The cloud functions call the Zalo Graph through a sealed relay in Vietnam

Date 2026-11-25 · Status accepted (the owner chose a relay on the shop's PC now and a Vietnam VPS later)

Decision: `zalo-session` and `zalo-phone` send their two Graph calls (`GET /v2.0/me` and `GET /v2.0/me/info`) through a small relay that runs in Vietnam (`pnpm zalo:relay`, `packages/zalo/src/relay-node`). Function and relay share one 256-bit key, the function secret `ZALO_RELAY_KEY`. Every request, every answer and every address announcement is sealed with AES-256-GCM under it. The additional data names the purpose, and for an answer the request id, so nothing can be swapped or replayed in another role. The relay listens on 127.0.0.1 only and is reached through a Cloudflare quick tunnel. It forwards only those two paths, with their own header sets (`access_token` and `appsecret_proof`, or `access_token`, `code` and `secret_key`) and an optional `fields` query. It refuses requests more than a minute old or new and request ids it has seen. It logs the path, the HTTP status, Zalo's error number and the time, never a header or a body. A quick tunnel gets a new address at every start, so the relay announces it to `zalo-session` every 5 minutes (`{"relay": <sealed {url, at}>}`, refused unless it opens, is at most two minutes off and names an https origin on a DNS name). The database keeps the newest address (`app.zalo_relay`, migration `zalo_relay`), and `zalo_relay_current()` answers it for 15 minutes. Without a key, or while no relay has announced itself, the functions call the Graph directly as before.

Why: on 2026-11-25 the cloud `zalo-session` refused every valid Mini App token with `401 zalo_token_refused`, and its log named the Graph error: `-501`. Forcing the function into five Supabase regions (Singapore, Tokyo, Mumbai, US East, Frankfurt) gave `-501` in each. The same token with the same proof, from the same Deno version, succeeds from the owner's PC in Vietnam, and the stored App secret matches the Zalo App's key (compared by SHA-256 digest only). The Graph evidently refuses servers outside Vietnam; others report the same from Cloudflare Workers. No Supabase region is in Vietnam. Sealing rather than only signing keeps the access token, the proof and, for the phone exchange, the App secret unreadable by the tunnel provider.

Not chosen: calling the Graph from the phone and trusting the answer (any user could claim any Zalo id); a plain HTTPS proxy with a shared header secret (the tunnel provider would read tokens and the App secret); a named tunnel or a fixed host now (needs a domain on Cloudflare; the VPS later gets a fixed name and the same announcements); waiting for Zalo support (the app stays broken meanwhile; a ticket can still ask).

Consequences: sign-in works only while the relay runs. On the PC that means while it is on and `pnpm zalo:relay` is running. A relay that cannot be reached answers `502 zalo_unavailable`, and with no recent announcement the Graph is asked directly, so `-501` again. Moving to a VPS in Vietnam changes where `pnpm zalo:relay` runs, not the code.

Built 2026-11-25: `packages/zalo/src/relay.ts` (sealing, allow-lists, replay guard, `relayFetch`), `src/function.ts` (`graphFetchFor`: the relay address asked at most once per request), `src/relay-node/server.ts` and `cli.ts` (the relay and its tunnel and heartbeat), `scripts/zalo-relay.mjs`, `zalo-session` (the announcement request, the relay for the sign-in and the customer phone exchange) and `zalo-phone`. Tests:
- `zalo:unit/relay` (17): the key's equivalence classes; envelopes opening only with the same key, purpose and context; tampering, a short iv and junk refused; the token never in clear text; which calls the relay carries (other hosts, http, other paths and methods, bodies, unknown headers, CR LF, odd queries); request freshness at ±60 s and ±60 001 ms; replays; answers bound to their request; address classes; announcement freshness at 120 s and 120 001 ms; `relayFetch` sealing on the wire, passing other calls through, and turning a refusing or forged relay into an upstream failure.
- `zalo:unit/relay-node` (9): the server forwarding and sealing; no token, proof, App secret or number in its log; junk, a wrong key, a replay, a stale request and a disallowed path refused without a Graph call; only `POST /relay`; the body limit; an unreachable Graph as 502; the command line's arguments, key path and cloud target; an announcement the function can open, with refusals reported without the address.
- `zalo-session:relay.test.ts` (8) and `zalo-phone:relay.test.ts` (1): only relayed Graph calls once a relay is announced, direct calls without one, no relay without a key, 502 for a relay that cannot be reached, 500 for a key of the wrong length, the announcement stored, and six refusals before the database.
- pgTAP `99_zalo_relay.sql` (26): privileges, row level security, address classes, newest wins, the two-minute future bound and the 15-minute freshness boundary.

## ADR-058 — Online ordering: server-priced orders, one status machine in SQL, pay at the counter through the Checkout SDK first, staff key orders into the till, delivery last

Date 2026-11-26 · Status proposed, amended on 2026-11-27 by ADR-060 to ADR-065 (the owner decided that customers see prices and order in the customer Mini App, at the table, for takeaway and later for delivery, paying at the counter first; the design is [deep-dives/online-ordering.md](deep-dives/online-ordering.md)). The amendments replace decision 1 (prices now come from the menu a native store owns), decision 2 (the status machine), decision 3 (payments), decision 4 (keying into the till and matching back) and decision 5 (the drift guard); the Zalo review rules, the Checkout SDK's MAC and webhook design, the table QR codes and the security design stand. Its first build is parked on the local branch `parked/ordering-pos-priced-menu`.

Context: Zalo's review policy (section 8) requires the Checkout SDK of any Mini App that creates orders, shows prices and has a payment function, and otherwise forbids showing prices; no page exempts payment at the counter, while the SDK itself offers a cash method (`COD`) and custom methods that need no payment provider. iPOS has no public write API (ADR-016), so an online order cannot reach the till by itself. The menu, prices and modifiers already arrive with the POS catalogue, which only a master-data run writes.

Decision:

1. **Prices.** An item's online price is the store's POS price for the order type (`app.online_item_price` over `items` and `store_items`), never a separate online price. `customer_place_order` takes item ids, quantities, options and the total the app displayed, computes every line and the total in SQL, refuses a different total as `price_changed` and stores a snapshot of names, prices and options. No function accepts a price from a client.
2. **One status machine owned by the database.** Fulfilment (`awaiting_checkout`, `placed`, `accepted`, `ready`, `out_for_delivery`, `completed`, `rejected`, `cancelled`, `expired`, `abandoned`, `delivery_failed`), money (`payment_status`) and the till hand-off (`till_state`) are three columns moved only by `security definer` functions that check the actor (the customer for their own order, staff in store scope, managers for money, Zalo through verified callbacks, the minute job), write an append-only `order_events` row and bump a version. Customer requests carry a `request_id`, staff actions the version they saw, Zalo callbacks their transaction id; a repeat gets the first answer. An order nobody accepts within the store's time-out (default 10 minutes) expires, and a store takes orders only while a staff device has polled its queue in the last 180 seconds.
3. **Pay at the counter first, through the Checkout SDK.** Tester builds may place orders directly; every public build sends each order through `CheckoutSDK.createOrder` with a MAC made in the Edge Function `checkout-order` from the brand's private key (a function secret named in `mini_apps`), forcing a counter method (a custom "Thanh toán tại quầy" method, or `COD`) for counter orders. The order reaches staff when `checkout-webhook` has verified Zalo's notify or callback (HMAC-SHA256, the amount, the order, an IP allow-list in observe then enforce mode). Staff record the payment at the till, and the server reports it to Zalo through the relay of ADR-057, extended to Zalo's payment API. Online methods (ZaloPay first) follow on the same path with refunds and a daily reconciliation.
4. **Staff key orders into the till; the sync matches them back.** The staff Mini App shows a polled queue with a sound; staff accept, prepare, mark ready or served, and key the order into the till under an online order source. `app.reconcile_orders`, run after every sync, matches the invoice by receipt number or by store, time window, source and amount, sends doubtful cases to a manager, and earns loyalty on a new matched path `F` through the existing earn rules; a staff-mode store turns the paid order into a bill capture (ADR-043). Pushing orders into iPOS is a reserved connector capability.
5. **Menu in step without new iPOS calls.** The online menu is a curated view (sections, visibility, display name, a description of at most 60 characters, photos, order, per-store availability) over the catalogue tables as they are. Synced sales whose menu price differs hide the item at that store and alert the owner, who refreshes the catalogue with one master-data run; a scheduled refresh is the owner's choice.
6. **Table QR codes** carry a 128-bit HMAC token per table and version, keyed per tenant in a table no API role reads; only its hash is stored, it is printed again from the key and rotated on demand.
7. **Delivery last**, on owner-defined areas without device location; receiver phones and addresses readable only by the store's staff while the order is open plus 24 hours, blanked 30 days after it ends.

Why: a price computed anywhere but the database could be changed by the client; one owner of every transition is the only way to keep three apps, two Zalo webhooks and a job from disagreeing about an order; going through the Checkout SDK from the first public release follows the literal review rule instead of betting on an exception, at no cost for the counter method; keying at the till is the only path iPOS leaves open, and matching after the sync reuses the reconciliation and loyalty rules already proven; reading prices from the POS keeps the online total equal to what the till charges.

Not chosen: an online price list kept by the owner (two prices drift, and the till would charge another amount); showing prices publicly before the Checkout SDK (the policy says to hide them); trusting the app's `checkTransaction` result (the client can lie; only Zalo's signed server call counts); Realtime as the only delivery channel to staff (WebSocket behaviour inside Zalo's WebView is unverified; polling first, Realtime later as a doorbell carrying no data); a nightly catalogue pull by default (iPOS calls are kept to a minimum); a radius from the customer's location for delivery (a location permission and sensitive data for little gain over areas).

Consequences: phases 1 to 7 ship to testers only, and the first public version with prices is the one submitted with the Checkout SDK; sign-in and the payment API depend on the relay in Vietnam until it runs on a VPS; the matrix of `pgtap:120` widens its scope to the ordering names; the ledger gains path `F`; staff need a counter device with the queue open. Open owner questions and the checks before each phase are in sections 14 and 15 of the deep dive.

Build: the thirteen phases of the deep dive's section 13, each with its migrations, functions, apps and tests (Sonnet for mechanical phases, a stronger model for prices, tokens, orders, the Checkout SDK, matching, payments and delivery).

Decision: this extends ADR-056 and keeps its rule that a brand's values live in its configuration and never in the repository. A brand that sets none of the new fields looks exactly as before.

1. **Optional colour roles.** A theme row may set, besides its twelve colours, `line_strong`; `badge` and `badge_ink`; seven status roles (`positive`, `negative`, `warning` with their soft fills, and `neutral_soft`); `inverse` and `inverse_ink`; up to four numbered tone groups (`tone_n`, `tone_n_ink`, `tone_n_soft`, numbered from 1 without a gap); and `art_plate`. Each group is all or nothing and is set in the light and in the dark palette alike. `app-config` checks 47 contrast rules (WCAG 2.2 AA: 4.5:1 for text, 3:1 for large text and interface parts; one is for large text only, and the table of the design spec is a unit test over the synthetic brand-3). A brand without a status group is checked against the design tokens' own status colours, because they are drawn on its surfaces whichever colours it chose; this closes a gap of ADR-056 for every brand. The shell's style sheet gives each role a default made of the design tokens and the twelve roles, so a brand that sets none is unchanged.
2. **Shape and type.** `theme.shape` sets corner radii (card, panel, control, field, tile, sheet, in steps of 0.5 px up to 32, 32, 24, 32, 32 and 40; the control may be `"pill"`), a border of 1, 1.5 or 2, an outline of 1.5 or 2 (drawn in the brand's ink) and a shadow on or off; `theme.type.body` is 15 or 16. Every field is optional and is validated as a bounded number or one word; the style sheet writes only those, once, and a hand-built theme cannot write anything else. Each utility of the shell (`rounded-card`, `rounded-field`, `rounded-control`, `border-card`, `border-outline`, `shadow-card`, `text-body` and the others) falls back to the value the literal class had, which a unit test compares with the Tailwind class it replaced, so the roughly 440 literal radius, border, shadow and body-size classes of both apps now read the tokens and a build without a shape is unchanged. Text fields keep 16 px, because iOS zooms a focused field below that.
3. **One way to write money, times and dates.** `formatVnd` writes 35.000đ (a dot every three digits, the đ attached), `formatVndDelta` the signed change with a true minus sign, `formatTimeRange` 07:00–23:00 and `formatDate` 26/11/2026, as plain functions without Intl; each refuses a value it cannot write. `PriceText` is the only way a screen writes a price: an element marked `data-price` with a hidden visible text and a spoken "35.000 đồng". A scan test keeps every other source from building a price, and a design check keeps every price-looking text inside such an element.
4. **A component kit** (status pills, stepper, option pills, chips with tones, sticky action bar, toast, six buttons) that reads only the roles and the shape tokens, and whose disabled state is the sunken fill and the muted ink, never an opacity.
5. **Route chrome** (flow routes without the tab bar, a slot above the tabs, a tab badge, scroll padding from the bars on screen) so that no focused control sits under two stacked bars; a route is `tabs` (the default) or `flow`, `aboveTabs` is a strip that floats on the tab bar of tab routes only, a tab's `badge` writes a count on its icon (99+ above 99) with a spoken text, and the shell turns the bars on screen (its own and those a screen registers) into three custom properties of the document so that the page and the scroll padding leave room for them, and scrolls the page's real scroller (ZaUI makes the body the scroller, and a browser does not scroll a control that is already in the viewport) when a focused control is covered.
6. **Decided, built next.** Fonts the brand selects from a vetted library of OFL fonts, shipped as files with a manifest and a checked hash and never as base64 in script or style, with a kill switch (this replaces the "custom fonts" line of ADR-056's "Not chosen": the concern there was the first-load script, and a font file adds none); brand art as SVG in named slots, read from the brand's own folder, sanitised by an allow-list that refuses what it cannot keep rather than stripping it, shown as an `<img>` and never inline (this replaces the "logo image" line); and copy overrides as a validated pack keyed by the catalogue's own keys, which keeps the tracked catalogues generic and free of brand words.

Why: the owner's brand handbook fixes its colours, shapes, fonts, characters and voice for every touchpoint, and the Mini Apps are the one touchpoint a customer uses daily; one validated mechanism lets a second brand follow by configuration alone and keeps the accessibility floor of ADR-034, while the byte-equality of an unthemed build keeps every existing screen as it was tested.

Not chosen: a style sheet per brand in the repository (brand data in a public repository); fonts from a font CDN (a request to another host, and Zalo's list of allowed domains); art inlined in the page or recoloured by the app (a script path, and the handbook forbids recolouring); a second set of components for themed brands (two kits drift); one global radius or one global shadow (the apps differ by design today, and the unthemed look must not move); applying the new look to every disabled button now (it would change the unthemed screens before the screens that need it are redesigned).

Consequences: the Mini App screens adopt the kit one group at a time (steps 11 and 12 of the design plan); a future `theme jsonb` column (G-108) must hold the same validated shape, with art as sanitised strings and copy as a validated pack; custom fonts may draw a reviewer's remark at Zalo's review (a risk of low to medium), and the kill switch builds a system-font version from the same configuration; the style baseline of both apps (`e2e/style-baseline.json`) must be recorded again when a screen's look changes on purpose.

Built 2026-11-27 (steps 1 to 7 of the design plan; the font, art and copy pieces come after): `packages/zalo-mini/src/app-config/index.ts` (the roles, the 47 rules, the shape and type, the style sheet), `src/styles/mini-app.css` (the defaults and the utilities), `src/format/` and `src/react/ui-kit/` (the formatters, `PriceText` and the kit), `src/react/mini-app-shell.tsx` and `bottom-bars.tsx` (the route chrome, the bars and `?route=` for Development builds), `src/testing/design-checks.ts` (the style baseline, the price, opacity and font checks), the synthetic brand-3 in `config/synthetic-brands.json`, and `ui.tsx` and the screens of both apps. Tests: `zalo-mini:unit/theme-roles` (207), `theme-shape` (41), `format` (103), `price-text`, `price-rule`, `ui-kit` (31), `dev-route` (7) and `shell-chrome` (39), the Tailwind checks `styles.test.ts` of each app (22), the `design-checks`, `design-brand3` and `chrome` Playwright specs (the last tabs through a page with two bars at the bottom), and the screen baselines of the customer (90 screens) and staff (156) apps.

## ADR-060 — A store can run on our platform as its till ("native" mode), with a menu and prices the managers own

Date 2026-11-27 · Status proposed (the owner chose on 2026-11-27 to make the platform the till of the first brand's store and to follow the brand's implementation plan strictly; the architecture is [deep-dives/native-till.md](deep-dives/native-till.md)) · amends ADR-058

Decision: each store has a till mode, `ipos` (the default: the POS is the till and we read it, as before) or `native` (orders, payments and the menu live here). Only an owner with every store changes it. Every price insert and change is written by a trigger to an append-only price log with who and when. Each order line snapshots the names and prices it was sold at. The POS catalogue (items, sizes, item types and its option groups, which the master-data run now also stores) may seed a brand's empty menu once; nothing keeps them in step afterwards.

Why: the brand's plan wants one source for the customer app, the counter and the website, so that switching an item off hides it at once and staff never key an order twice; a POS that cannot take orders by API (ADR-016) cannot be that source. Owned prices with a log keep the history auditable, and line snapshots keep old orders and reports stable when prices change.

Not chosen: online prices derived from the POS (ADR-058 decision 1; the POS stops being the till); a separate online price list beside the POS (two lists drift); keeping the menu in step with the POS after the import (two masters).

## ADR-061 — Native orders follow one fixed lifecycle with a separate payment status, enforced by the database

Date 2026-11-27 · Status proposed (the owner's plan fixes the six states and the counter rules) · amends ADR-058

Decision: an order is `awaiting_payment`, `accepted`, `preparing`, `ready` (takeaway) or `serving` (table), `completed`, or `cancelled`, the last only from `awaiting_payment` or `accepted`. The database refuses every other transition, whatever a screen sends. Payment status (`unpaid`, `paid`, `refund_pending`, `refunded`, `partially_refunded`) moves separately: an order paid online leaves `awaiting_payment` only through the server's confirmation of a verified gateway or bank notification; a pay-at-counter order enters the queue at once as `accepted` and `unpaid` and is completed only after the counter records its payment; takeaway is prepaid. Every transition writes an append-only event with its actor; every cancellation and refund is logged with who, when and the amount. Customer requests carry an idempotency key, staff actions the version they saw. Order numbers count per store and business day and are given when an order is accepted. A completed and paid order becomes an invoice of the store in the sales facts, through a POS account of connector `native`, so reports keep working. One stamp per drink is added when an order completes, to the customer's Zalo account (no phone), nine giving a free tenth drink as a reward; a cancellation or refund takes the stamps back.

Why: the counter, the customer app and the payment notifications must never disagree about an order, and only a single owner of every transition, with its log, can guarantee that (acceptance criteria 3 and 4 of the plan). Keeping money apart from fulfilment lets a table order be prepared before it is paid at the counter while still forbidding its completion.

Not chosen: ADR-058's eleven-state machine with acceptance by staff and expiry (the owner's lifecycle has no staff acceptance step); trusting the client's payment result; stamps through the phone-matched loyalty paths (the first release has no phone).

## ADR-062 — Online payment through the Checkout SDK and a dynamic VietQR, confirmed only by the server

Date 2026-11-27 · Status proposed (the owner's plan adopts three ways to pay) · amends ADR-058 decision 3

Decision: customers pay with e-wallets through Zalo's Checkout SDK, by bank transfer to a dynamic VietQR whose bank notification arrives automatically through a provider adapter (a mock first; the provider is chosen with the bank), or in cash or by card at the counter. Every attempt is an `order_payments` row with an idempotency key and is moved only by a service-role confirmation that a webhook calls after verifying the provider's signature and the amount; a duplicate notification answers the first outcome; a minute job re-queries an attempt whose notification is late. Refunds are `order_refunds` rows. Provider secrets live only in Edge Function secrets.

Why: staff should never have to check a bank account, the customer's device can lie, and a lost notification must not leave a paid order waiting or create a second one (acceptance criterion 3).

Not chosen: transfers confirmed by staff looking at the bank app (the earlier spec); a pay-at-counter custom method through the Checkout SDK as the only way (ADR-058's first public path stays possible for counter orders when Zalo's review requires it).

## ADR-063 — The server issues an e-invoice for every paid order through a provider-agnostic adapter

## ADR-066 — The counter web app: its own app in the monorepo, Zalo's web login through a new function, browser printing first, a chime unlocked once per shift

Date 2026-11-28 · Status proposed (builds ADR-064; the owner's plan, phase 1; the design is [deep-dives/counter-app.md](deep-dives/counter-app.md))

Decision:

1. **Where it lives.** `apps/counter`: Vite, React, TypeScript and Tailwind like the other apps, a hash router, installable as a PWA (a manifest and a small service worker that keeps the app shell for a reload without network), the screen kept on through the Wake Lock API where the browser has it, landscape on a 10–11" Android tablet in Chrome and on an iPad in Safari, and the same app on a manager's phone with bottom tabs instead of the rail. It reuses what `packages/zalo-mini` has that does not need the Zalo runtime: the theme style sheet and its utilities, the formatters, `PriceText` and the component kit (exported now as `@fnb/zalo-mini/ui-kit`, `@fnb/zalo-mini/i18n` and `@fnb/zalo-mini/app-config`); the brand's look comes from the same configuration as its staff Mini App (the generated `app-config.json` of the brand, or the synthetic configuration), so the code stays generic.
2. **Zalo's web login.** A new Edge Function `counter-session` runs Zalo's OAuth v4 with PKCE: the browser makes and keeps the verifier; the function names the authorise page with a state sealed (AES-GCM) under a key derived from the App secret that binds the challenge, the return address and ten minutes; at the callback it checks the state (CSRF and code injection), exchanges the code with the App secret and reads the person from the Graph, both through the relay of ADR-057, which now also carries that one token exchange (a POST of exactly four form fields; never a refresh). The person is mapped to a member by the same `zalo_session_sign_in` and `zalo_session_pair` as the staff Mini App (one Zalo App per brand holds both Mini Apps and the web login, so the user id is the same); only owners, managers and staff get a session. A person the roster does not know gets none, is recorded in `app.blocked_signins` for the managers (M02, acceptance criterion 5) and receives a sealed ten-minute ticket with which they may type the pairing code a manager gives them (the existing first-time path) and accept the staff notice. Return addresses are an exact list (`COUNTER_REDIRECT_URIS`), and CORS lets in only their origins.
3. **Printing.** v1 prints the 80 mm ticket through the browser's print dialog with a print style sheet (`@page` 80 mm wide, monospace-sized type, nothing but the ticket). The app talks to a `TicketPrinter` interface (`print(ticket)`, `status()`); the browser printer is its first implementation, and an ESC/POS printer over WebUSB or Web Bluetooth is a second one later, with the same ticket model.
4. **Sound and attention.** A short chime made with Web Audio (no audio file) when the board shows an order it had not seen; browsers allow sound only after a tap, so the app asks for one tap per shift ("Bật âm báo") and remembers it for the shift; vibration where the device has it; an order waiting longer than the store's `late_order_minutes` is drawn red with the word "Chờ lâu", never by colour alone.
5. **Offline.** The board keeps the orders it shows and its cursor; back online it asks from the last cursor and says how many orders arrived meanwhile. Actions are not queued offline: buttons that change an order say why they are off.
6. **Roles on screen.** Staff see Đơn, Bàn, Món, Ca làm; owners and managers also Quản lý, on the tablet and on the phone. The database decides every action again (`counter_*`, `manager_*`); hiding is never the control.

Why: the plan wants the counter always open with sound and printing, on a tablet, without a Zalo review; a separate app keeps the counter's bundle small and its CSP tight, and sharing the Mini Apps' theme and kit keeps one look. Reusing the staff Mini App's identity functions keeps one rule for who may enter. A sealed state and ticket need no new table and cannot be forged or read by the browser. The print dialog works on every device today; ESC/POS needs a printer model chosen with the owner.

Not chosen: a second Mini App for the counter (the plan); a username and password; a state table in the database (a sealed state does the same with nothing to clean up); keeping the PKCE verifier on the server (the browser holding it is the standard public-client flow and binds the code to that browser); queuing order actions offline (a later conflict with another device is worse than a clear "no network" on the button); a sound file (Web Audio needs no asset and no network).

Consequences: the Zalo App's callback list must hold the counter's address, and `COUNTER_REDIRECT_URIS` the same; the relay on the shop's PC must be updated to carry the token exchange; staff who already paired in the staff Mini App sign in without a code; the manager PIN at the counter (design Q02, D3) and the cashier's reason for a cash difference are not in the database yet, so a difference is confirmed from the manager's own device with the reason in the note.

Built 2026-11-28 on the branch `counter-app`: the counter-session function and migration `counter_sign_in`; `apps/counter` with Đơn, Tạo đơn, Bàn, Món, Ca làm and Quản lý (menu and prices, the day, requests, staff, shifts, QR codes); the printer seam with the browser printer. The design, its deviations from the drawn screens and the tests are in [deep-dives/counter-app.md](deep-dives/counter-app.md) sections 2 to 8.

## ADR-067 — Online payment goes through provider adapters: the database owns the money, an adapter only shapes, proves and asks

Date 2026-11-28 · Status proposed (builds ADR-062 for phase 1 of the owner's plan; the merchant accounts, and so the real providers, come later)

Decision:

1. **The seam.** A `PaymentProvider` (`packages/payments`, `@fnb/payments`) has four operations and no say over an order: `createPayment(attempt)` turns an attempt the database opened into what the device needs (the Checkout SDK's `createOrder` parameters with their MAC, or a dynamic VietQR payload with the bank's details) and its expiry; `verifyNotification(request)` proves a webhook came from the provider and reads it into neutral events (the provider's transaction id, the amount, success, the attempt's reference when the provider carries it back, else the reference-shaped words of a transfer's text); `queryStatus(ref)` asks about an attempt whose notification is late; `refund(ref, amount)` and `queryRefund(id)` send and follow a refund. Whether an event pays an order is decided only in SQL (ADR-068).
2. **Two methods, three adapters.** `zalo_checkout`: Zalo's Checkout SDK (the createOrder MAC over the sorted parameters, the callback's `mac` in Zalo's fixed order and `overallMac` over every sorted key, the notify's `mac`, and the server APIs `getOrderStatus`, `createRefund`, `getRefundStatus` and `purchase-payment`, each signed over its fields and the private key). `vietqr`: the server builds the EMVCo payload itself (NAPAS GUID, BIN, account, `QRIBFTTA`, VND, the exact amount, the reference as the purpose, CRC-16/CCITT-FALSE) and a bank-notification adapter proves the watching service's posts: `sepay` (an API key in `Authorization: Apikey`) and `mock` (HMAC-SHA256 over the time and the raw body, five minutes either way), for tests and local development, refused live and wherever `PAYMENTS_MOCK=on` is not set. Further services (PayOS, Casso) are one adapter each.
3. **Configuration rows, secrets by name.** `payment_providers` holds per brand (and, for a VietQR, optionally per store: the most specific row decides) the method, the adapter, the mode `off | sandbox | live`, the name of the Edge Function secret with the key (`ZALO_CHECKOUT_KEY_<BRAND>`, `PAYMENT_BANK_<NAME>`; a CHECK refuses a pasted value) and the public settings (a forced wallet; the bank BIN, bank name, account number, account name and reference prefix). Only an owner with every store of the brand writes it, through `checkout_set_provider`, and each change is logged with before and after in the append-only `payment_provider_changes`, because a changed account number redirects customers' money. A store's `payment_methods` follow its providers at once, so nothing offers online payment unless a provider is on; the customer app also needs its `VITE_ONLINE_PAYMENT` build flag.
4. **References.** Each attempt gets a reference of a prefix (2 to 4 capitals; `ZC` for the Checkout SDK) and 8 characters of an alphabet without 0, 1, I and O, drawn in the database (40 bits) and unique; it is the transfer's purpose and the Checkout `extradata`. A pending attempt is resumed under a new idempotency key with the same reference, so reopening the QR never makes a second one.
5. **Zalo's payment API through the relay.** `payment-mini.zalo.me` may refuse servers outside Vietnam as the Graph does (ADR-057); the relay's allow-list gains exactly the four calls with their fields (two GETs of three query fields, two JSON POSTs of four or five, a 64-hex MAC, an amount from 1 to 100,000,000, resultCode 1, 0 or −1, the purchase path naming the body's app); nothing else, and the private key never travels.

Why: the owner's plan wants e-wallets and an automatically confirmed bank transfer now and the real merchant accounts later; keeping every money decision in one SQL function and every provider detail behind four operations lets a provider be switched on, swapped or added by configuration and one adapter, with the mock exercising the whole path today.

Not chosen: Zalo's own bank-transfer method chosen in the Checkout sheet (its notify carries no amount, so nothing could confirm a transfer automatically); a payment page of a gateway outside the Mini App (forbidden by Zalo's review); storing keys in the database (rows name secrets); a separate table of provider events (the payment rows, the exceptions and the order events already record each outcome once).

Consequences: the bank-transfer popup (`Payment.openCheckoutPopup`, beta until 03/2027) declares VietQR to the platform, and the job reports each paid popup with `purchase-payment`; the relay on the shop's PC must be updated before the cloud can re-query or refund; the request formats of Zalo's server APIs (query or body) are not written in Zalo's pages and must be confirmed in the sandbox; SePay's adapter follows its public page and must be confirmed in its sandbox.

Built 2026-11-28 on the branch `customer-ordering`: `packages/payments` (65 unit tests), the relay's payment allow-list (`zalo:unit/relay-payment`, 11), migration `online_payments`, the functions `checkout-order`, `checkout-webhook`, `bank-webhook` and `payments-job` (ADR-068), and the customer app's and the counter's payment steps.

## ADR-068 — Verified provider news settles in one SQL function; money that cannot be applied goes to a manager, never to an order

Date 2026-11-28 · Status proposed (builds ADR-062; acceptance criteria 1, 3, 4 and 6 of the owner's plan)

Decision:

1. **Four functions.** `checkout-order` (session required) opens or resumes an attempt for the caller's own order, or for a counter order of a store the staff member works at (VietQR only), and answers the createOrder parameters or the VietQR; it also links Zalo's order id after `createOrder` or the popup. `checkout-webhook` (no session) takes Zalo's callback and notify, finds the brand by `appId`, checks `mac` and `overallMac` in constant time, and checks the source address against Zalo's two documented addresses in observe or enforce mode. `bank-webhook/<provider id>` (no session) takes the bank service's posts, proven by the row's adapter and key. `payments-job` (a single-use ticket from the minute job `checkout-tick`) re-queries late attempts, sends and follows wallet refunds, and reports paid popups to Zalo.
2. **One settlement.** `checkout_settle` is the only path from provider news to money, for the webhooks and the job alike: serialised and unique per provider transaction (a repeat answers its first outcome; Zalo's duplicate is `returnCode: 2`); the attempt is found by the job's payment id, by the exact reference, or by exactly one of a transfer's candidates under the same provider; a failure fails a pending attempt; the exact amount for a pending attempt, in time, for an unpaid order pays it through `checkout_payment_confirm` and accepts it with its number (T3).
3. **Never applied, always kept.** Another amount (a partial or a larger transfer), money after the attempt expired or failed, a VietQR after its window or for a cancelled order, a second payment of a paid order, and a reference nobody issued go to `payment_exceptions`, once per provider transaction, with an event on the order: the manager queue (`manager_payment_exceptions`, `manager_resolve_payment_exception`: handed back or dismissed, with a note). A transfer without any reference is ignored (the account receives other money). The one exception to "never applied": a wallet payment that arrives for its pending attempt after the order was cancelled becomes a due refund, which the job sends back through `createRefund` (criterion 4), because the wallet can refund and a bank transfer cannot.
4. **Late and lost news.** The job asks Zalo about a linked Checkout attempt from 3 minutes old, every 3 minutes for an hour, then hourly, and refuses an answer whose `extradata` names another reference (a client that linked another of its orders). The minute job fails what nobody will settle: a VietQR once its order is cancelled or paid otherwise or its window passed; a Checkout attempt 30 minutes after its window without Zalo's order id, 24 hours after with one.
5. **What the clients see.** The apps poll the order (`customer_order`, `counter_order`); `checkTransaction` and the popup's answer only choose the screen. Nothing a client sends can pay an order.

Why: a gateway and a bank service post twice, late, out of order and in parallel, and the device can lie; a single serialised settlement with a manager queue for everything ambiguous keeps the owner's rule that only the server, on the provider's word, moves an order to accepted, and that money is never silently lost or doubled (criterion 3).

Not chosen: auto-confirming a partial or late transfer (the plan says never); refunding transfers automatically (no bank service here refunds; a manager hands them back); answering Zalo `returnCode: −1` for money kept in the queue (it moved, and the queue takes responsibility); trusting `checkTransaction` (the client).

Consequences: the owner's Checkout settings need the callback and notify URLs; the bank service needs the `bank-webhook` URL with the provider id and the key; `checkout-tick` must be scheduled (`app.enable_checkout_jobs`); a manager watches the queue (an alert for open exceptions is a follow-up); the daily reconciliation (criterion 6) counts only applied payments, so an open exception is money the day does not include until it is resolved.

Built 2026-11-28 (see ADR-067): pgTAP `290_online_payments` (99), rows in `03`, `47`, `120` and `121`; Deno tests of the four functions and the shared redaction (28); `payments:integration/parallel-settle` (gated, see test-plan.md). The same day migration `payment_exception_readers` gave the queue's reader the status `resolved`, the resolver's name and the account that received the money, without changing who reads which (pgTAP `302_payment_exception_readers`, 39), and the counter's VietQR runs end to end against the real `checkout-order` (`counter:e2e/vietqr`).

## ADR-069 — E-invoices go through a provider adapter; the database owns every document and fixes every amount when the job takes it

Date 2026-11-28 · Status proposed (builds ADR-063 for phase 1 of the owner's plan: "mỗi đơn thu tiền xong, máy chủ tự xuất hóa đơn qua API của nhà cung cấp hóa đơn"; the provider is not chosen yet, so only the mock runs) · the design is [deep-dives/native-till.md](deep-dives/native-till.md) section 17

Decision:

1. **The seam.** An `EInvoiceProvider` (`packages/einvoice`, `@fnb/einvoice`) has six operations and no say over what is owed: `issue` (the sale invoice of a paid order, or a company invoice with a buyer), `query` (the document made under our id, or none), `replace` (a company invoice replacing an issued one), `adjust` (by an amount, negative for a refund), `cancel` (or `unsupported`) and `lookup` (the lookup code and address). Every call names our document id, which every provider keeps as its own idempotency key. The invoices are of the kind made from a cash register (a series whose fourth character is `M`): the provider needs no signature of ours and passes them to the tax authority the same day. Failures are classes only (`timeout`, `unavailable`, `rate_limited`, `rejected_auth`, `not_configured`, `unknown` are retried; `rejected_data`, `rejected_duplicate`, `unsupported` need a person), never the provider's text, which may repeat the buyer's data.
2. **One record per document.** `e_invoices` holds the sale invoice of a paid order, the company invoice that replaces it, and each correction (an adjustment, or a cancellation when nothing is left), with the state machine `queued → issuing → issued | failed`; a failed document is retried after 1, 2, 4 … minutes (at most an hour) and given up after 10 attempts of a round, or at once for a class that needs a person, which raises `einvoice_failed` to owners and managers; a sale invoice becomes `replaced` or `adjusted`, any document `cancelled`. It holds the provider's reference, number and series, the lookup code and address, the tax authority's code, the attempts and the last error class, and no buyer data (the company request holds it once).
3. **Queued by the money, computed by the job.** Triggers on an order's payment status and on a succeeded refund call one reconciliation per order (serialised): a paid order of a store whose provider is on gets its sale invoice; when nothing is held any more, documents that never reached the provider are cancelled there, without a call; when a document is or may be at the provider and what it holds may differ from what the order holds, one correction is queued. The job fixes the amount when it takes a document: a sale or company invoice for what the order holds (paid less refunded), a correction for the difference with what the provider holds. Two partial refunds before the job comes, a refund while the invoice is on its way, a payment undone and taken again: whatever their order, nothing is counted twice and an amount of zero settles the correction here.
4. **One job, one claim per document.** The minute job `einvoice-tick` posts a single-use ticket to the Edge Function `einvoice-job` (the pattern of `payments-job`), which takes up to 10 documents under a 5-minute claim each (`for update skip locked`; a lapsed claim is taken again), sale invoices first, a company invoice once its sale invoice is issued, a correction once nothing of its order is on its way. Every attempt after the first asks the provider for the document by our id before making it, and a result is recorded only under the claim it was given (a late or second answer is `stale`), so neither a lost answer nor two overlapping runs make a second invoice. A cancellation the provider refuses becomes an adjustment to zero: decree 70/2025 removed the cancellation of a valid invoice, and a provider may replace it with one of zero value instead.
5. **Configuration rows, secrets by name.** `einvoice_providers` holds per brand (and, for a store that invoices under a tax code of its own, per store: the most specific row decides) the adapter, the mode `off | sandbox | live`, the name of the Edge Function secret with the credentials (`EINVOICE_KEY_<NAME>`; a CHECK refuses a name shaped like a pasted value) and the seller's public settings (tax code, template 1 or 2, the six-character series of a cash register, the VAT rate or `none` for a household business's sales invoice). Only an owner with every store of the brand writes it (`einvoice_set_provider`), and every change is logged with before and after in the append-only `einvoice_provider_changes`. The mock is refused live and runs only where `EINVOICE_MOCK=on`.
6. **What staff and managers see.** `counter_order_einvoice` gives the counter's pill of an order (`pending` "Đang xuất…", `issued` "Đã xuất", `retrying` "Chưa xuất được. Hệ thống tự thử lại, đơn vẫn hoàn tất.", `failed`, `cancelled`, `off`, `none`) with the lookup address; `manager_einvoices` lists the failing documents of a store with their error class, `manager_retry_einvoice` sends one again (a fresh round that still asks first).

Fixing amounts when the job takes a document is what makes refunds, undone payments and company invoices compose without double counting, whatever order they arrive in.

Not chosen: issuing from the payment functions themselves (a provider outage would hold up a payment); a correction per refund with its amount fixed when queued (two refunds before the job, or a refund during an issue, would count twice); cancelling an invoice at the provider for a refund (decree 70/2025 removed it; an adjustment, or a zero-value replacement where the provider does that, is the lawful path); keeping the buyer's data on every document (one copy, on the request, for the legal period); a real email provider in this step (the interface and its mock only; most providers email the buyer themselves).

## ADR-070 — A company invoice is asked for once per paid order, inside the store's window, and replaces the sale invoice; saved companies belong to the customer

Date 2026-11-28 · Status proposed (builds the C18 screen and Q01's company row of the missing-screens design; decision D5 there: 7 days, replace) · the design is [deep-dives/native-till.md](deep-dives/native-till.md) section 17

Decision:

1. **The rules, all on the server.** `customer_request_invoice` (C18) takes the caller's own order and a company (tax code, name, address, email) or one of their saved companies, and refuses in this order: a malformed request (`22023`), `rate_limited` (10 calls an hour per customer, 1,000 per tenant), `unknown_order` (another customer's order answers like an unknown one), `unknown_company`, `request_conflict` (the same request id with other content; the same content is a replay), `already_requested` (one per order), `einvoice_off`, `not_paid`, `refunded` (any refund due, pending or done, or a cancelled order), `nothing_to_invoice`, `window_passed` (after the last day: the payment's local date plus the store's `company_invoice_days`, 7 by default, 1 to 30), and `invalid` with the fields in error. The tax code is trimmed and must read `^\d{10}(-\d{3})?$` (13 bare digits gain their hyphen); the name holds 1 to 200 characters and the address 1 to 300, on one line, without control characters or `< > { }`; the email at most 254 characters with a local part of at most 64, no leading, trailing or double dot. `counter_request_invoice` is the same for a counter order, keyed by staff of the store.
2. **Replace, never two.** A request queues the company invoice, which waits until the order's sale invoice is issued and then replaces it: in the same step the sale invoice becomes `replaced` and the request `issued`, so an order never has two valid invoices. Its amount is what the order holds when the job takes it. Then the email goes through the mailer interface (the mock) unless the provider sent it; the request reads `received → issuing → issued → emailed`, or `failed` (given up, with the alert; the sale invoice stays valid) or `cancelled` (the order was refunded before anything reached the provider).
3. **Saved companies.** "Lưu công ty này cho lần sau" keeps up to 10 companies per login in `saved_companies`, which row-level security shows to that customer alone (no member reads them); `customer_saved_companies` lists them, `customer_delete_saved_company` deletes one, and `customer_delete_account` deletes them with the login. The requests stay with their invoices for the legal period, without the link to the login, and the customer's export holds both.

Why: the design's server rules (C18) and its tests (C18-U, I, S) are the contract; a request that replaces rather than adds keeps the books equal to the money, and one copy of the buyer's data, with the request, is all the invoice needs.

Not chosen: a second invoice beside the retail one (the design says "Em không xuất hai hóa đơn cho một đơn"); a company invoice for a refunded order (the provider's replace-after-adjust rule is not known yet; the counter's manager can issue it in the provider's portal); a saved company visible to the store (it is the customer's address book); checking the company's name against the tax code (the customer checks, as the design's copy says; a provider may refuse an unknown code, which gives up the request with the alert).

Consequences: the customer app's C18 screens and the counter's company row are the other agent's to wire (the functions are ready); the window and the replace rule must be confirmed with the accountant and the chosen provider (decision D5).

## ADR-071 — A refund counts on the business day it is handed back; a later day's refund is its own negative document

Date 2026-11-28 · Status proposed, reversible (defect D-1 of [test-plan.md](test-plan.md) section 10.15; acceptance criterion 6 of the owner's plan; the owner has not decided yet: this is the default) · the design is [deep-dives/native-till.md](deep-dives/native-till.md) sections 11 and 12

Decision:

1. **The day of a refund.** A succeeded refund counts on the business day it is handed back: for cash, the business day of the shift whose drawer paid it out (the drawer the clock-out counts, `app.shift_cash_flow`); for card and online refunds, the store's business day at the instant the refund succeeded, under the store's day start as the rest of the native till; never before the order's own business day (a night shift begun the evening before keeps its drawer's date, which can precede the order's). One function decides it, `app.refund_business_date(refund)`.
2. **A later day never changes an earlier one.** A refund of the order's own business day edits the order's invoice, or voids it when it is refunded in full, with an invoice event, as before. A refund of a later business day leaves the order's invoice as it was (amounts, status, payments, the day's aggregates) and is its own document of the refund's day, written through the sync's columns: external id `native-<order id>-refund-<refund id>`, the new `invoice_status` value `refund`, gross 0 (a deduction from revenue, as a same-day refund is), net and paid minus the refund, one payment of minus the refund in its method, no line, no receipt number, phone or customer. The refund day is marked for the analytics refresh. The writer is idempotent and also runs at completion.
3. **The readers.** A refund document is in every sum and in no count: never an invoice, a sale, a visit or an e-invoice sale. The daily and hourly facts and the aggregates sum it into net, paid and cash and leave it out of `invoices`, of the payment aggregate's invoice count, of the zero-sales alert, the voucher spike, data quality, member share and the capture rate; Tổng quan ngày, the web app's Hôm nay and the export's daily check do the same; `export_control_totals` counts the documents (`refund_invoices`). iPOS data has no such document (an iPOS edit or void changes the invoice itself), so nothing existing is reused; no report so far distinguishes a return, so none gains a figure.
4. **The day's reconciliation.** `manager_day_reconciliation` subtracts each refund on its own day: the revenue and the card and cash invoiced follow the documents of the day, and the gateway's figure takes off the confirmed online refunds of completed orders that count on the day. Two figures explain, outside the match, what cancelled paid orders do to the drawers: `cash_refund_owed` (cash still owed back for the day's cancelled orders) and `cancelled_cash` (their net cash in the day's drawers, whose opposite is the difference they cause).
5. **E-invoices (ADR-069) agree.** The e-invoices follow the order's money, not the sales facts: a later day's refund queues one correction when it succeeds, and the job issues it when it takes it, dated that day (on or after the refund's); the sale invoice keeps its amount and becomes `adjusted`, as the order's invoice of the earlier day keeps its amount. A sale invoice not yet issued when a later refund succeeds (the provider down for a day) is issued for what the order then holds, with its "Giảm trừ đã hoàn tiền" line; the two days of the sales facts still add up to it. Stamps are untouched by the rule: they are taken back in proportion to the money whatever the day.

Why: in Vietnamese accounting a return or allowance is booked when it happens, as a deduction from that period's revenue (account 521, deductions from revenue), and the e-invoice adjustment is dated the day it is issued; a closed day whose drawers were counted must not change afterwards, or criterion 6 can never hold for both days. Before this, a later day's refund edited or voided the order's invoice while the cash left the refund day's drawer, so neither day matched although every drawer and the gateway were right.

Not chosen (the other choice, kept a small change): the refund counting on the order's own day. It is `app.refund_business_date` answering the order's business date: every refund is then of the same day, edits or voids the order's invoice, writes no document, and the reconciliation subtracts it on the order's day (both days then show a difference, which an explanation line would have to carry). Also not chosen: one document per order and day (a refund's own document keeps its reason, method and provider reference); a negative quantity on item lines (a refund is an amount, as a same-day refund is); counting a refund document as an invoice with a negative amount (every average and visit count would move).

Consequences: the owner confirms the rule or chooses the other one (test-plan.md section 10.15, question 2); the reports read refunds on the day they were handed back, so a day of refunds alone has a negative net and no invoice; a store-day can show a negative revenue on screen (the counter writes it with its minus sign); the export's manifest names `refunds` beside `voided` when there are any.

Built 2026-11-28 on the branch `d1-refund-day`: migrations `invoice_status_refund` and `refund_business_day`; pgTAP `301_refund_business_day` (79), `299_acceptance_day_reconciliation` (54, the two TODO tests of D-1 turned on and the explanation of a refund still owed); `counter:unit/manager`, `web:metrics/today`, `web:exports/totals`; `counter:e2e/shift` (the cash of a cancelled order on Đối soát ngày).

## ADR-072 — A takeaway books a slot of the one day the server offers; the unpaid order is the hold, checked under a lock per slot

Date 2026-11-28 · Status proposed (the owner's plan, phase 2: "Mang đi và hẹn giờ lấy, kể cả đặt trước khi quán đóng cửa"; the design's C17 and its D7 and D9) · the design is [deep-dives/native-till.md](deep-dives/native-till.md) section 19

Decision:

1. **The server's clock and one day.** The slots a customer may book come from the server's clock in the store's zone, never the phone's: `customer_takeaway_slots` answers today while a slot is left after now plus the store's preparation time, else the next opening (closures and the business-day start included). While the store is closed (`closed_now`, `last_orders_passed`, `closed_today`) the slots start at its next opening and "Càng sớm có thể" is not offered. The app sends no date: there is no other day to book.
2. **Slots on the clock.** A slot starts every `takeaway_slot_minutes` (a divisor of an hour, 15 by default) on the store's clock from each opening to its closing less one slot (the last pick-up); a time that is not a slot start is refused (`pickup_time_invalid`), so a tampered value cannot book between slots. Each slot takes `takeaway_slot_limit` orders (6 by default; the design leaves the count to the owner). The preparation time is the store's one `prep_minutes`.
3. **The unpaid order is the hold.** A booking holds its place from its placement while its payment is open: 10 minutes, the payment screen's "đơn giữ 10 phút", or the store's payment window when shorter. Its place is free again the instant the window passes, before any job runs, and at once when the order is cancelled. No function holds a place without an order; the open-order limit (three) bounds the places one customer can hold. A customer may move their own unpaid booking to another slot while the hold lasts; the hold keeps its end.
4. **One winner for the last place.** Placement and the move check the slot under a transaction advisory lock of the store and the slot, taken before the count, so the second of two customers counts the first's committed order and is refused `slot_full`.
5. **Paid, then scheduled.** A booking enters the counter's queue only once paid. It belongs to the business date of its pick-up (its number and its revenue are that day's). Until its preparation start (pick-up less preparation) it is `scheduled`: shown apart, not counted towards `busy` or late.
6. **The ready message through the customer outbox.** A takeaway of a member's Zalo account turned ready queues the customer message `takeaway_ready` (ADR-030's outbox, the routing of phase 19a): consultation inside the free window, else the ZBS template `order_ready` between 06:00 and 22:00 when the tenant's ZBS is on and the template approved, else in the app; it lives an hour, so the night window closes it in the app (ADR-065: after 22:00 the app alone). A visitor without a phone has the order screen only.

Why: a slot booked on the phone's clock or a date the app chose could be tampered with or simply wrong; an order that holds its place only once paid would let two customers pay for the last place; a separate hold record would need its own expiry, limits and cleanup, while the unpaid order already has all three (its payment window, the open-order limit, the minute job). Filing a morning booking under the morning keeps each day's numbers, revenue and reconciliation whole (ADR-071's reasoning).

Not chosen: any day in the future (the plan allows the next opening only when closed); slots aligned to the opening instead of the clock (an opening at 07:10 would give 15:10 slots); a settings row per weekday for the limit (the owner has not asked; one number per store); refusing a payment that arrives after the hold ended (money is never refused: it is applied, and the slot may take one order over its limit in that gap).

Consequences: the counter shows bookings apart until their start and lets managers set the three numbers; the customer app offers takeaway only in a build that pays online, where the store offers it; ZBS stays off until the owner's templates are approved, and the tests send through the mock.

Built 2026-11-28 on the branch `c17-takeaway`: migrations `takeaway_slots`, `takeaway_ready_message`, `takeaway_asap_while_closed`; pgTAP `304_takeaway_slots` (69), `305_takeaway_placement` (72), `306_takeaway_ready_message` (25).

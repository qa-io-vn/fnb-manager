# Database schema

Field dictionary for the canonical, POS-agnostic schema in `supabase/migrations/`. Everything here is derived from the migrations; when they change, this file changes with them. Nothing in this document is specific to one shop: identifiers, keys and payloads are illustrative shapes only.

Two schemas exist:

- `public` holds every table and enum and is exposed through the Data API to the `authenticated` and `service_role` roles. `anon` holds no privilege on it.
- `app` holds helper functions used by row-level-security policies and triggers. It is not exposed through the API; `authenticated` may execute the helpers, nothing else.

## Conventions

- Every table has a `uuid` primary key `id` generated by `gen_random_uuid()`, except `tenant_members` (composite key) and `pos_account_tokens` (keyed by the account).
- Every row that belongs to a tenant carries `tenant_id`. Rows that belong to a store also carry `store_id`; rows that come from one POS account carry `pos_account_id`.
- Identifiers assigned by a POS are kept verbatim in `external_id` columns (`text`). Foreign relations to POS entities are expressed by external id, never by our uuid, so a re-synced catalogue never breaks facts.
- Timestamps are `timestamptz`. Calendar days are `date`. Money is `numeric(14,2)` in the tenant's currency. Quantities are `numeric(12,3)`. Percentages are `numeric(6,3)` where `1.100` means 1.1 %.
- Master-data tables carry `active`, `first_seen_at` and `last_seen_at`, maintained by the sync: a row disappearing from the POS catalogue is marked inactive, never deleted.
- Manual-input tables carry `created_by` (defaults to `auth.uid()`, frozen by a trigger on update), `created_at` and `updated_at` (set by a trigger).
- No table is ever written by the browser except the manual-input tables, `strategy_reports` and the two legal ledgers `consent_records` and `data_subject_requests`; every other write comes from the sync jobs and the messaging jobs running as `service_role`.

`strategy_source` says how a plan reached the database: `skill` when the local strategy skill published it, `routine` when a scheduled cloud routine did, `pasted` when a person pasted it in the web app.

`legal_form` records the owner's entity type under the personal-data law: a household business or micro-enterprise is exempt from the cross-border transfer dossier, a small enterprise may defer it, an enterprise must file it. `unknown` is the default until the owner confirms. `e_invoice_status` says whether the store's POS issues cash-register e-invoices. `tran_no_reset_period` says how often the POS restarts its receipt numbering, which is why receipt claims are keyed on store, business date and receipt number together.

`opening_hours` is an object keyed by weekday `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun`. Each value is a list of `[open, close]` pairs in local `HH:MM`, so a split day is two pairs and a closed day is an empty list or a missing key:

```json
{"mon": [["07:00", "22:30"]], "sat": [["07:00", "12:00"], ["16:00", "23:00"]]}
```

### Catalogue tables synced per POS account

`item_types`, `item_classes`, `units`, `packages`, `customizations`, `sources`, `payment_methods`, `promotions` and `devices` share one shape: `id`, `tenant_id`, `pos_account_id`, `external_id` (unique per account), `name`, `active`, `raw`, `first_seen_at`, `last_seen_at`, plus the specific columns below.

| Table | Extra columns | Meaning |
| --- | --- | --- |

| `item_classes` | — | Coarser grouping above item types (for example drinks versus food) |
| `units` | — | Units of sale |
| `packages` | `list_price` numeric(14,2) null | Combos sold as one line |
| `customizations` | — | Modifier options such as sugar or ice level |
| `sources` | — | Order channels such as dine-in or takeaway |
| `payment_methods` | `kind` payment_kind not null default `other` | Tenders; `kind` is the canonical classification used by shift cash and payment-mix reports |
| `promotions` | `starts_at`, `ends_at` timestamptz null | Promotion catalogue with validity window |
| `devices` | `code`, `name`, `store_external_id` text null; `store_id` uuid null | POS terminals; `store_id` is resolved by the sync and set to null if the store disappears |

## Consent and legal records

These tables implement the duties of the personal-data law and the anti-spam decree described in ADR-021: a per-purpose consent ledger with evidence and a working opt-out, data-subject requests tracked against their statutory deadlines, and an outbound-message log kept at least one year.

### `consent_records`

Append-only ledger of consent. One row per grant; a revocation sets `revoked_at` on the row instead of deleting it, so the evidence of both events survives. At most one active row (`revoked_at` null) exists per (`tenant_id`, `subject_type`, `subject_id`, `purpose`), enforced by the partial unique index `consent_records_one_active_per_subject_purpose_key`; a new grant after a revocation is a new row.

#### Append-only rule

The trigger `consent_records_keep_grant` (`app.keep_consent_grant()`, before update) enforces the ledger for every role, the service role included, because it is a data rule rather than an access rule. Every column except `revoked_at` is frozen once the row exists: an update that touches `tenant_id`, `subject_type`, `subject_id`, `purpose`, `policy_version`, `channel`, `granted_at`, `evidence` or `created_at` fails with `consent_records is an append-only ledger: only revoked_at may change`. `revoked_at` may go from null to a timestamp once; clearing it or moving it fails with `consent_records revocation is final`, and a value before `granted_at` fails with `consent_records revocation cannot precede the grant`. `authenticated` holds no `DELETE` privilege on the table, so a wrong grant is corrected by revoking it and recording a new one.

| Column | Type | Null | Meaning |
| --- | --- | --- | --- |
| `id` | uuid | no | Primary key |
| `tenant_id` | uuid | no | Tenant |
| `subject_type` | consent_subject | no | `customer` or `staff` |
| `subject_id` | uuid | no | `customers.id` for a customer, `tenant_members.user_id` for staff; no foreign key, so the record outlives the subject row and the two subject kinds share one column |
| `purpose` | consent_purpose | no | `loyalty`, `marketing` or `staff_ops` |
| `policy_version` | text | no | Version label of the privacy notice the subject agreed to |
| `channel` | text | no | Where the consent was captured: `mini_app`, `oa_form`, `till`, `web`, … |
| `granted_at` | timestamptz | no | Moment of consent |
| `revoked_at` | timestamptz | yes | Moment of withdrawal; must not precede `granted_at`; null while active |
| `evidence` | jsonb | yes | Proof of the act, for example the form payload, a checkbox state or a signed-notice reference |
| `created_at` | timestamptz | no | Row creation |

Indexes: (`tenant_id`, `subject_type`, `subject_id`, `purpose`) and the partial unique index above.

`app.has_active_consent(tenant, subject_type, subject, purpose)` returns true when an active row exists. It runs with the caller's privileges, so under RLS a member sees only the consent of their own tenant; the messaging jobs call it as `service_role` before every send.

#### Deadline rule

`app.dsr_deadlines(received, country_code, time_zone, uses_processor)` returns the two deadlines:

- `first_response_due_at` is `received` plus two working days. A working day is Monday to Friday in `time_zone` that is not a global `holidays` row (`tenant_id` null) of `country_code`; tenant-specific custom holidays do not count. Counting starts on the day after receipt and keeps the time of day, so a request received Friday 10:00 is due Tuesday 10:00, and one received on 29 April is due 5 May because 30 April, 1 May and the weekend are skipped. The function scans the 120 days after receipt and raises an exception if it cannot find two working days in that window, so the deadline is never silently null.
- `completion_due_at` is `received` plus 20 calendar days, or 30 when `uses_processor` is true.

The trigger `data_subject_requests_fill_deadlines` runs before insert, reads the tenant's `country_code` and `timezone`, and fills whichever of the two due columns was left null. Values given explicitly are kept.

## Row-level security

Every table in `public` has RLS enabled. `anon` holds no privilege on any table. `authenticated` holds `SELECT` on every table except `pos_account_tokens`, `INSERT`, `UPDATE`, `DELETE` only on the manual-input tables (`item_costs`, `payment_fee_rates`, `item_type_roles`, `holidays`, `targets`) and `strategy_reports`, and `INSERT`, `UPDATE` without `DELETE` on the legal ledgers `consent_records` and `data_subject_requests`. Default privileges are set so that a future table created by the migration role starts read-only for `authenticated` and invisible to `anon`. The sync jobs run as `service_role`, which bypasses RLS.

### Roles

| Role | Purpose | Reads | Writes |
| --- | --- | --- | --- |
| `owner` | Tenant owner | Everything of the tenant within store scope, plus `outbound_messages`; `data_subject_requests` only when the membership is not store-limited, because the policy requires an unlimited store scope, so a store-limited owner reads zero requests | Manual inputs and plans within store scope; consent records (grant, or revoke by setting `revoked_at`); data-subject requests when the membership is not store-limited |
| `manager` | Store or tenant manager | Same as owner, including the zero-request rule for a store-limited membership | Same as owner |
| `staff` | Cashier or shift lead | Everything of the tenant within store scope, including `consent_records`; no `data_subject_requests`, no `outbound_messages` | Nothing |
| `viewer` | Read-only stakeholder | Same as staff | Nothing |
| `publisher` | Service identity used by the plan-publishing skill or routine | `tenants`, `stores`, `strategy_reports`, `holidays` only | Insert into `strategy_reports` |

`owner`, `manager`, `staff` and `viewer` are the data roles. `publisher` is deliberately outside them so that a leaked publisher credential cannot read a single sale.

### Store scope

`tenant_members.store_ids` limits a member to some stores of the tenant. A null scope means every store. Store-scoped fact tables filter on `store_id`; tenant-wide catalogue tables filter on `tenant_id`; tables whose `store_id` may be null (`item_costs`, `payment_fee_rates`, `strategy_reports`) show tenant-wide rows to every member of the tenant and store rows only to members who can see that store.

### Helpers in schema `app`

Every helper sets an empty `search_path`. The membership helpers (`data_roles()` through `can_read_store()`) are `security definer` and `stable`, and read `tenant_members` for `auth.uid()`. `has_active_consent()` and `dsr_deadlines()` are `security invoker`, so they see only what the caller may see. `set_updated_at()`, `keep_created_by()`, `keep_consent_grant()` and `fill_dsr_deadlines()` are trigger functions; only `fill_dsr_deadlines()` is `security definer`, because it must read the tenant row of a request filed from the browser.

| Function | Returns | Used by |
| --- | --- | --- |
| `data_roles()` | The four data roles | The two data helpers below |
| `current_user_tenant_ids()` | Tenants of the caller in any role | `tenants`, `strategy_reports`, `holidays` |
| `current_user_data_tenant_ids()` | Tenants of the caller in a data role | Every other tenant-filtered table |
| `current_user_store_ids()` | Stores the caller may see in any role | `stores`, `strategy_reports` |
| `current_user_data_store_ids()` | Stores the caller may see in a data role | Every other store-filtered table |
| `has_tenant_role(tenant_id, roles[])` | Caller holds one of the roles in the tenant | Available to policies and application code |
| `has_store_scope(tenant_id, store_id, roles[])` | Caller holds one of the roles and the store is in scope; a null `store_id` requires an unlimited scope | The two wrappers below |
| `can_manage_store_scope(tenant_id, store_id)` | `has_store_scope` with `owner`, `manager` | Insert, update and delete on manual inputs; update and delete on plans |
| `can_publish_store_scope(tenant_id, store_id)` | `has_store_scope` with `owner`, `manager`, `publisher` | Insert on `strategy_reports` |
| `can_read_store(store_id)` | Caller may see the store | Application code; no policy calls it per row |
| `set_updated_at()` | Trigger | Every table with `updated_at` |
| `keep_created_by()` | Trigger | Every table with `created_by` |

| `has_active_consent(tenant, subject_type, subject, purpose)` | An active consent row exists | Application code and messaging jobs; `security invoker`, so RLS applies to the caller |
| `dsr_deadlines(received, country_code, time_zone, uses_processor)` | The two statutory deadlines of a data-subject request; raises when no second working day lies within 120 days | `fill_dsr_deadlines()` and application code; `security invoker` |
| `fill_dsr_deadlines()` | Trigger | `data_subject_requests` before insert; `security definer` so it can read the tenant row |

Policies call the array-returning helpers as `(select app.helper())` so Postgres evaluates them once per statement, not once per row.

### Who can write what

| Table | Insert | Update / delete |
| --- | --- | --- |
| `item_costs`, `payment_fee_rates`, `targets` | `can_manage_store_scope(tenant_id, store_id)` and `created_by = auth.uid()` | `can_manage_store_scope(tenant_id, store_id)` |

Tenant-wide rows (null `store_id`, or tables without one) can be written only by owners and managers whose membership is not limited to some stores. `created_by` must equal the caller on insert and is frozen by trigger afterwards, so attribution cannot be forged.

## Business date

`invoices.business_date` is assigned by the sync, never by the database, with this rule:

```
local_time     = sold_at at time zone stores.timezone
business_date  = (local_time - make_interval(mins => stores.business_day_start_minutes))::date
```

A store with `business_day_start_minutes = 300` (05:00) books a sale at 00:30 local time to the previous calendar day; with the default 0 the business date is the local calendar day. Store timezones are IANA names, so a zone with daylight saving is handled by Postgres. `invoice_payments.business_date` copies the invoice value. Shifts keep their raw timestamps; reports attribute a shift to the business date of its `opened_at` using the same rule.

## Storage rule for `raw`

Storage on the free tier is finite, so the sync keeps:

- `invoices.raw` and `shifts.raw`: the full payload the POS returned for the sale or the shift, so any future column can be back-filled without a re-sync.
- `invoice_lines.raw`: only the fields that are not already on the invoice row and not mapped to a line column. Fields duplicated from the invoice (store, receipt number, timestamps, cashier, customer) are dropped by the sync before the write.
- `invoice_payments.raw`, `invoice_events.raw`, master data `raw`: the payload of that entity as returned.

This is a sync-side rule: the database accepts any JSON; the connector's normaliser is where the pruning happens and where it is tested.

## Tenant-consistent composite foreign keys

A row that carries both `tenant_id` and a reference to a child of the tenant (a store or a POS account) references the pair, not the child's id alone:

`stores` and `pos_accounts` declare `unique (tenant_id, id)`; every store-scoped table declares `foreign key (tenant_id, store_id) references stores (tenant_id, id)` and every account-scoped table declares `foreign key (tenant_id, pos_account_id) references pos_accounts (tenant_id, id)`.

The database therefore refuses a row that names tenant A together with a store of tenant B, even when written by the service role or by a bug in a policy. Tables that follow the pattern: `stores`, every catalogue table, `store_items`, `devices`, `invoices`, `invoice_lines`, `invoice_payments`, `invoice_events`, `shifts`, `sync_runs`, `sync_checks`, `item_costs`, `payment_fee_rates`, `item_type_roles`, `targets`, `strategy_reports`. `invoice_events.invoice_id` references `invoices.id` alone with `on delete set null`, because the event must outlive the invoice; its `store_id` and `invoice_external_id` keep it attributable. The legal tables carry `tenant_id` and no store; `consent_records.subject_id` and `data_subject_requests.subject_id` deliberately have no foreign key (see the consent model), and `outbound_messages.consent_record_id` references `consent_records.id` alone with `on delete set null`.

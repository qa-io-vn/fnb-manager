# Web app specification (apps/web)

Scope: roadmap phases 6 (foundation and "Hôm nay"), 9 (periodic reports), 10 (thematic reports, settings), 11 (exports, data pack, Kế hoạch), the web page of 14a (Cài đặt → Nhân viên, the staff roster and pairing codes), the web pages of 14b (Cài đặt → Checklist, Vận hành, the staff contact note and the operations cards on two themes) and the web pages of phases 16 to 18 (Cài đặt → Khách hàng thân thiết with its programme and reward catalogue, the Khách hàng section and Khuyến mãi's redemption card). This document is the contract the builders implement; `docs/metrics.md` defines every number shown, `docs/schema.md` the tables and functions read.

## Stack and constraints

- Vite + React + TypeScript, deployed to GitHub Pages by `.github/workflows/deploy-web.yml` (the workflow builds `apps/web` when `apps/web/package.json` exists; `VITE_BASE_PATH` comes from the Pages configuration, `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from repository variables).
- Routing: hash router (`#/…`) so a project-site base path and the fixed Pages 404 behaviour never matter; supabase-js configured with `flowType: 'pkce'` so auth redirects do not collide with the hash (ADR-023). Password-reset and invite links must be tested on the deployed path.
- Data access: supabase-js only, as the signed-in user; row-level security carries the protection, so the bundle may contain the publishable key and nothing else. Reads go to the phase 8 functions and aggregate tables; writes only to the manual-data tables, consent/data-subject tooling and `strategy_reports`, and since phases 14 to 18 to the loyalty programme, staff-phone and reward tables and through the staff, checklist, operations and loyalty functions (the "Settings writes" row of [Data access](#data-access)). Lists paginate with a stable order under the 1,000-row API default.
- State: tenant (from membership; a selector appears only when the user belongs to several), selected stores (multi-select with "Tất cả"), period (ngày / tuần / tháng / năm / tùy chọn), language (the tenant's default language until the member picks one with the toggle, then the device's choice), persisted in `localStorage` as conveniences only.
- Formatting through `Intl` with the tenant's locale and currency: VND shows no decimals and large values use a compact "tr ₫" / "tỷ ₫" headline form with the exact value in a tooltip; dates `dd/MM/yyyy`; weekdays in Vietnamese; percentages one decimal. No currency or locale string is hard-coded.
- Internationalisation: Vietnamese and English message files under `src/i18n/messages/` (one pair per area, see Phase 9 decisions) with a completeness test (every key in both; every user-visible string through `t()`); report sentences and metric explanations are templates in these files, not code. Vietnamese follows the metric registry's spelling ("hóa đơn", "hủy", "tùy").
- Performance: initial JS ≤ 400 kB gzipped excluding the lazily loaded ECharts chunk; Lighthouse mobile performance ≥ 85, accessibility ≥ 90; axe with no serious violations; WCAG 2.2 AA (ADR-034); 16 px side gutters; no horizontal scroll at 360 px.
- Freshness: `version.json` written at build time; the app compares it on focus and shows "Có phiên bản mới — tải lại" because Pages caches `index.html` for ten minutes.
- No comments in code; descriptive names and small components instead.

## Layout

Mobile first. A top bar with the tenant and store selector, period picker and language toggle; a bottom navigation on phones (Hôm nay, Báo cáo, Chủ đề, Kế hoạch, Cài đặt) and a side rail on wider screens. The rail has a second group, "Khách hàng và vận hành" (`nav.secondary`), with Khách hàng (`#/khach-hang/thanh-vien`) and Vận hành (`#/van-hanh/checklist`), each shown only to the roles that can open the page (`visibleSecondaryItems` in `src/shell/navigation.tsx`: Khách hàng for owners, managers and viewers, Vận hành for owners and managers); it reads the membership only while the rail shows, so phones load nothing for it, and phones reach the sections by their links. Every report page is a vertical stack of report cards.

The thematic reports add two rows under the page heading: the theme tabs (a labelled `nav` of eight links at least 44 px high that scrolls inside its own box on a phone, keeps the active tab in view and is hidden in print), and the range picker (the seven presets as a radio group, ‹ and › that step by the range's length and are marked `aria-disabled` at either end, a line announced politely with the dates, the day count and the reference, and two dates bounded from 1 January 2023 to the as-of day, applied on Enter, on blur or after a pause). A shortened range, an end moved back to the last complete day and an unreadable range each show a notice that stays while that range is shown. Settings pages, the theme pages, Vận hành and Khách hàng hide the top bar's period control (`sectionsWithFixedPeriod` in `src/shell/top-bar.tsx`); Vận hành and Bất thường theo ca use the same range picker with their own summary line.

## ReportCard contract

Every report is built from one component with these parts, in this order:

1. **Headline** — one metric from the registry, formatted compactly, with the exact value on hover.
2. **Comparison chips** — vs previous period and, when history exists, vs same period last year or the same-weekday baseline; colour follows the metric's `direction` from the registry (higher-is-better green when up).
3. **Sentence** — one plain-language explanation generated from a template in the i18n file with driver attribution (which weekday, category or item moved the number most), rendered from the data, never from a model.
4. **Chart** — ECharts, lazy-loaded, with the accessible table underneath as the fallback. A chart with two to six categories, such as one bar per store, shows every category label and wraps it to its category's width, measured after each render and resize, so no store name disappears on a phone; a chart with more categories (hours, days) lets crowded labels hide each other. While printing, charts redraw at the 660 px print width.
5. **Table** — sortable, with a CSV download (UTF-8 with BOM) of the rows in the order shown. `buildCsv` in `src/lib/csv.ts` writes two dialects: `comma` (the default, byte for byte phase 9's output) and `semicolon` (semicolons and a decimal comma, for an Excel set to Vietnamese regional settings). Both start with `EF BB BF`, end lines with CRLF, quote a text cell holding a comma, a semicolon, a quote or a line break, keep the formula protection, write numbers without thousands separators (money rounded to two decimals, percentages to one) and never a `sep=` line. The dialect is the device preference `preferences.csvDialect`, handed to every table through `CsvDialectProvider` (`src/state/csv-dialect.tsx`), so every table of phases 9 and 10 follows it; its chooser is the "Thiết bị này" box of Cài đặt → Ngưỡng báo cáo. `src/lib/csv-parse.ts` reads the files the cost import of phase 10b takes: `parseCsv` (each record with the line it starts on, BOM stripped, comma, semicolon or tab chosen by its count outside quotes on the header line, RFC 4180 quoting with quotes opening only at the start of a cell, CRLF, LF or CR, blank lines skipped; a quote that never closes gives `unterminatedQuote`, and text after a closing quote gives `textAfterQuote`, each with the line the quoted cell opened on, so a stray quote can neither swallow the rows after it nor hide them behind a later quoted cell), `parseMoneyCell` (a unit at either end and the spaces around it dropped; for VND only plain digits or groups of three after a first group that is not zero, with one consistent mark among dot, comma and space, so a fraction is refused rather than read a hundred times too large; for a currency with decimals the last dot or comma followed by at most its decimals is the decimal mark; an amount of more than 15 digits is refused rather than rounded), `parseDateCell` and `detectDateOrder` (ISO always; slash dates as `dmy` or `mdy` when some cell is a real date in that order only, `conflict` when cells prove both, otherwise `unknown`; a date that exists in neither order proves nothing). A figure's cell may hold a state instead of a number: a message key in a value column (money, count, ratio, percent and the like; `isValueColumn` of `@fnb/reports`) is shown and exported in words, as So sánh's "chưa thiết lập" and "chưa có dữ liệu kỳ trước" are, while `null` stays "—"; `tableKeys` lists those keys so the message checks cover them, and sorting puts such a cell after every number in both directions, as it does an empty one (`sortRows` with the table's columns). A card may cap a long table at its first rows (`previewRows` of the table model): the rest follow "Xem tất cả n dòng" and fold again under "Chỉ xem n dòng đầu", sorting applies to every row before the cap, and the CSV and the printed page always hold every row.
6. **Giải thích chỉ số** — collapsed definitions from the registry (formula, grain, convention, what is missing when provisional).

A card may also carry controls, placed after the headline and before the chips (the optional `controls` slot of `ReportCard`): a theme parameter renders there as a labelled select or radio group (`src/themes/theme-param-controls.tsx`), reachable by keyboard and hidden in print. An option the theme disables may carry a reason (`ThemeParamOption.reasonKey`), shown under the control in small type and tied to the option with `aria-describedby`, so a screen reader hears why it cannot be chosen. The slot stays empty for every phase 9 card and for a theme card without parameters. A loading card and a card whose call failed keep their controls, so another value can still be chosen, and when a change makes the card reload, the control that changed gets the focus back unless the reader has moved it elsewhere.

Cards show a `provisional` marker when the registry says an input is missing (no costs, no seats, no customer identity) and a `chưa đối soát` marker when the underlying days are not verified.

## Phase 6 decisions

Points the specification leaves open, as built in phase 6:

- **Row source.** Hôm nay reads the fact tables (`invoices`, `invoice_lines`, `invoice_payments`, `payment_methods`, `holidays`, `sync_runs`, `sync_checks`) through one `RowSource` interface and computes every number client-side in one metrics module (`src/metrics/today.ts`), because the phase 8 SQL layer was still changing. The planned phase 9 switch of the Supabase implementation to `v_recent_daily_sales`, `v_recent_hourly_sales` and `same_weekday_baseline` is withdrawn ("As-of rule" under Phase 9 decisions), so Hôm nay still reads the fact tables. The demo is the second implementation.
- **Paging the sales tables.** The sync deletes and re-inserts the lines and tenders of every upserted invoice, so their `id` changes on each run. Invoices, lines and tenders are therefore read with keyset pagination on keys that survive a re-sync — `id` for `invoices`, (`invoice_id`, `external_id`) for `invoice_lines`, (`invoice_id`, `sequence_no`) for `invoice_payments` — and rows are de-duplicated by that key, so a sync committing between two page requests neither drops nor doubles a row.
- **Baseline for an unfinished day.** Today's cards compare the sales so far with the same-weekday median of the previous 8 weeks **up to the same time of the business day** ("so với mức nền cùng thứ đến 10:15"); yesterday compares whole days. The hourly baseline curve is always the whole-day median per hour. With several stores the days are summed per date before the median, and the average-ticket baseline is the median of the daily averages, matching `same_weekday_baseline()`.
- **Hour axis.** Hours come from `sold_at` in the store time zone and the axis starts at the hour of the first selected store's `business_day_start_minutes`, so a 00:30 sale under a 05:00 day start appears at the end of its business day. Today's curve ends at the current hour; later hours have no value (a gap in the chart, "—" in the table) instead of zero.
- **Badges.** The freshness badge sits in the top bar and uses the latest `sync_runs` row with status `succeeded` for the tenant. The verified badge sits on each day section of Hôm nay (today, yesterday) and reads "đã đối soát" only when every selected store-day of that section has a matched `sync_checks` row; cards repeat "chưa đối soát" as their marker. In demo mode both badges read "dữ liệu mẫu".
- **Period picker.** Shown on every route whose period is selectable; hidden on Hôm nay, whose days are fixed. The stored period keeps its kind and custom range, but a day, week, month or year anchor chosen on an earlier day moves to today when the app loads.
- **Top bar on phones.** Below 1024 px the store, tenant and period controls fold into one summary button ("Tất cả · Ngày 08/11/2026") that opens them, so the sticky bar stays short; from 1024 px they are always shown. The demo banner sits inside the sticky bar (a one-line form on phones) so it stays visible at every scroll position, and the new-version prompt is a toast above the bottom navigation on every screen, sign-in screens included.
- **Page titles and focus.** Every screen sets the document title to "<screen> · FNB Manager" in the current language and moves focus to its heading after an in-app navigation.
- **Compact money.** The number uses the tenant locale; the unit word comes from the interface language (`tr` / `tỷ` in Vietnamese, `M` / `B` in English).
- **Auth routes.** `#/dang-nhap` (login), `#/quen-mat-khau` (reset request; the e-mail link returns to `#/mat-khau-moi`), `#/mat-khau-moi` (new password after the recovery link).

A configured build offers "Xem bản demo" on the login page for the browser session, with "Thoát bản demo" in the top bar. Each generated store-day is cached and produced in its own task, so the generator never blocks the main thread for long; a demo build preloads the demo module and every chunk it imports from `index.html`, and none of them loads zod.
- **Icons and install.** `public/favicon.svg` (a bar chart on the accent colour, no shop name) is the only drawn source; `scripts/render-icons.mjs` renders `favicon.ico` (16, 32 and 48 px), `apple-touch-icon.png` (180 px) and the manifest icons (192 and 512 px, plus a maskable 512 px with the glyph inside the safe zone) with Playwright's Chromium, and the PNGs are committed. `manifest.webmanifest` names the app "FNB Manager" (short name "FNB"), opens standalone, and keeps `start_url` and `scope` relative to the manifest, so the same file works at `/` and under the Pages base path. Theme and background colours are the light `--surface` token, and `index.html` sets `theme-color` per colour scheme; a unit test keeps these in step with `styles.css`. There is no service worker.
- **Print.** A4 portrait with 12 mm margins. The colour tokens switch to black on white whatever the screen scheme; the navigation, the demo banner, the new-version prompt, buttons, form controls and closed "Giải thích chỉ số" panels are not printed; the store and period summary prints as a line of text; report grids print one card per row and a card is not split across pages when it fits on one. In development builds `#/thiet-ke` shows every shared control with its variants; the production build leaves the page out.

A colour changes in the token files and nowhere else.
- **Tables on phones.** A report-card table that is wider than its card scrolls inside the card, never the page. Playwright checks at 360 px that the last column of every table can be brought into view and that the page itself never scrolls sideways.

A comparison chip keeps its value on one line and wraps only its label.

## Phase 9 decisions

Periodic reports Ngày, Tuần, Tháng and Năm (`#/bao-cao/ngay|tuan|thang|nam`), as built in phase 9. ADR-029 records the main choice.

- **Data path.** Every report number is computed in SQL by `security invoker` functions (`docs/schema.md`, "Report functions (phase 9)"), called through `supabase.rpc()` as the signed-in member, so row-level security applies unchanged. TypeScript adds only what sits on top of SQL rows: changes, the exact decomposition, like-for-like selection, rankings, statuses and sentence drivers. The demo runs `@fnb/demo-analytics`, a TypeScript port of exactly those functions over the generated days, behind the same `AnalyticsSource` interface; a parity suite holds the port to the SQL. `AnalyticsSourceProvider` (inside `RowSourceProvider`) loads the live or demo source lazily, the first time a report page asks for it, so other screens never download the report code.
- **Loading.** A report is a `ReportDefinition` from `@fnb/reports`: primary calls, follow-up calls planned once `store_coverage` has answered, and cards. Each call is one TanStack query keyed `["analytics", source kind, tenant, function, arguments]`, so reports share identical calls. A card shows as soon as the calls it needs have answered, keeps its previous content dimmed and marked "Đang tải…" while a new period loads, and turns into an error card with a retry when a call fails or its model cannot be built; a call refused for going over a size limit (`22023`) asks for fewer stores or a shorter period instead of offering a retry. Calls planned twice with the same arguments (the like-for-like calls of last period and last year over the same stores) share one query. Ranges that end before the day before the as-of day stay fresh for 30 minutes, recent ones for 2 minutes with a refetch on focus, and demo results never go stale; the previous period's primary calls are prefetched when the browser is idle.
- **As-of rule.** Reports end at the last complete business day: `asOfDate()` is the earliest store business date of now minus one, recomputed when the tab becomes visible again. Hôm nay owns the running day; a link to today on a report shows yesterday with the notice "Ngày hôm nay chưa kết thúc; báo cáo dừng ở ngày …" and a link to Hôm nay; a link to a period that has not started shows the latest period with "Kỳ này chưa bắt đầu; …" and rewrites the URL to that period. Hôm nay keeps its fact-row path: the plan to move it to `v_recent_daily_sales`, `v_recent_hourly_sales` and `same_weekday_baseline` is withdrawn, because those views take about 84 ms for every visible store on each select. In demo mode Hôm nay and the reports read one shared cache of generated days, so Hôm nay's yesterday equals Ngày's day.
- **Periods and deep links.** Ngày is one business day, Tuần the ISO week (Monday to Sunday, week to date), Tháng the calendar month, Năm the calendar year, each ending at the as-of day. The URL is the source of truth: `#/bao-cao/ngay?date=2026-11-07`, `#/bao-cao/tuan?week=2026-W45`, `#/bao-cao/thang?month=2026-10`, `#/bao-cao/nam?year=2026`, plus `&store=<id>,<id>` when the selection is not "Tất cả". A missing or invalid period is replaced by the period of the as-of day; unknown store ids are ignored. Previous and next, the date picker and the tabs push a history entry; normalisation and store changes from the top bar replace it. A typed date moves the report only once it is complete: on Enter, when the field loses focus, or after it has stayed unchanged for 700 ms, and further dates picked while the field keeps focus replace that entry. The step buttons stay focusable at the first and last period (`aria-disabled`), and the period label is a polite live region, so a screen reader hears each new period. A store parameter in a link updates the stored selection, and a period change stores the period as the top bar's period. Stepping does not move focus; the heading takes focus only when the path changes. The top bar hides its period picker on report routes, where the period navigator replaces it.
- **Card model.** Cards are pure functions from SQL rows to a language-neutral `CardModel` (headline, comparisons, decomposition, narrative parts, tables, chart, notice, markers) in `@fnb/reports`. One adapter (`src/reports/card-adapter.ts`) turns every model into `ReportCard` props (a headline in the `signedMoney` unit, such as Khuyến mãi's net lift, carries a + before a gain and a − before a loss): fraction metrics compare in percentage points ("+1,2 điểm %"), every other unit as a relative change; an unavailable comparison shows its state ("chưa có dữ liệu năm trước"); tables keep their CSV download with a UTF-8 BOM, a second table gets its own file; charts may use a right axis, stacks, horizontal mark lines and category mark areas, and mount when they come within 200 px of the viewport, once the page has painted twice more and the main thread is idle, so the ECharts download never delays the first cards (at once when printing). The same models will feed the data pack, KPI follow-up and digests.
- **Coverage rule.** A store counts for a comparison when its history starts on or before the first day of the reference period. When every selected store counts the comparison uses all stores; when some do, it compares the covered stores only and says so ("so với cùng thứ năm trước · cùng cửa hàng (1/2)"); when none does, a store that opened later reads "chưa có dữ liệu năm trước" (or "kỳ trước") instead of a number. The baseline is never like for like. Cards that read item, payment or shift aggregates show "đang cập nhật" while a store has a recent day whose aggregates lag the live totals.
- **i18n files.** `src/i18n/messages/` holds one Vietnamese and one English file per area: `core` (every phase 6 string), `metrics` (`metric.*`, the label, formula, grain and convention of every metric and display series a card names), `reports` (`report.*` strings shared by all reports: comparison labels, unavailable states, decomposition and driver clauses, table labels, navigator and tabs) and one file per report (`report-day`, `report-week`, `report-month`, `report-year`). `catalog.ts` merges them statically; a test checks each pair for equal keys, non-empty values, equal placeholders, the file's prefix and no key in two files, and another runs the four reports on the demo engine and checks every key they produce exists in both languages. `docs/reports/cau-van-bao-cao.md` lists every template of the four reports with its English meaning and placeholders, for the owner's wording review.
- **Demo calendar.** The demo tenant's two stores, opening dates, closed Tết days, seasonality, menu changes and targets come from `@fnb/demo-analytics`; the demo row source reads the same generated days, maps line kinds with the sync's `toDbLineKind` and excludes holidays and Tết days from Hôm nay's baseline. "Cửa hàng mẫu 2" always opens 8 to 13 weeks before the current month, so the young-store states are always visible.
- **Size.** The initial JS stays under 400 kB gzipped; `scripts/check-size.mjs` treats the ECharts chunk, the demo modules, the four report pages and the live analytics source as lazy (each pattern must match at least one chunk); `@fnb/core`, `@fnb/metrics`, `@fnb/reports`, `@fnb/sync`, `@fnb/connector-mock` and `@fnb/demo-analytics` are marked free of side effects, so the bundler can split them: the entry chunk holds no zod, and the demo row source reaches only the date rules and the generator. A demo build also preloads the demo engine chunk and everything it imports.

## Phase 10 decisions

Thematic reports under `#/chu-de/…`, as built so far: Doanh thu & xu hướng, Giờ & ngày trong tuần, Thực đơn and Thanh toán & tiền mặt in phase 10a, and Khuyến mãi & giảm giá, Ca & két tiền, So sánh cửa hàng and Chất lượng dữ liệu in phase 10b ([doanh-thu.md](reports/doanh-thu.md), [gio-ngay.md](reports/gio-ngay.md), [thuc-don.md](reports/thuc-don.md), [thanh-toan.md](reports/thanh-toan.md), [khuyen-mai.md](reports/khuyen-mai.md), [ca-ket-tien.md](reports/ca-ket-tien.md), [so-sanh.md](reports/so-sanh.md), [chat-luong.md](reports/chat-luong.md)). Theme cards size to their content, so a short card beside a long one keeps its own height. ADR-035 and ADR-036 record the main choices.

- **Theme definitions.** A theme is a `ThemeDefinition` of `@fnb/reports`: primary calls, follow-up calls (which receive the primary rows as well as the coverage), cards and a maximum range. Its cards build the phase 9 `CardModel`, so `ReportCard`, the adapter, CSV, print and "Giải thích chỉ số" are shared. A card's notice carries at most two Settings links (`action` and `secondaryAction`, both `report.action.*`), for a card whose findings are fixed on two Settings pages. `themeDefinitions` holds all eight themes, so its type requires every kind; the tabs (`themeTabEntries`) list them in roadmap order, and an unknown slug under `#/chu-de` opens Doanh thu with the search kept. A tab moves the range to the target theme's maximum (`moveRangeToLimit`), so a 52-week range opens Ca & két tiền on its last 92 days. A card marked `wide` spans the whole card grid from tablets up, like a heat table, and in a wide card text cells stay on one line (the pinned first column only from tablets up, so it stays narrow on a phone), except a column holding text longer than 24 characters, which wraps within its minimum width so its last column stays reachable on a phone.
- **Ranges and deep links.** `src/themes/theme-route.ts` reads `range` or `from` and `to` and `store`, and writes the canonical form back with a replace; a user's step pushes a history entry. Presets, clamps (400 days, the as-of day), steps and references are pure functions in `@fnb/reports` (`resolveRange`, `stepRange`, `rangeOfPreset`). The last preset used is a per-device preference (`themePreset`), used when a link carries no range; moving between themes keeps the range (clipped to the target's maximum) and the stores. The top bar's period control is hidden on these pages, which have their own range picker.
- **Loading.** `src/reports/use-cards-load.ts` holds the phase 9 loading logic generalised over a plan (`useCardsLoad`): one TanStack query per distinct call, keyed `["analytics", source kind, tenant, function, arguments]`, follow-ups once coverage has answered, the stale times of phase 9 (a range of several days counts its latest end), and the range before prefetched when the cards have settled. `useReportLoad` and `useThemeLoad` are thin wrappers, so phase 9's behaviour and tests are unchanged.
- **One source for both registries.** The live source is `createRpcReportSource` and the demo source `createDemoReportSource`; both answer the phase 9 functions through `call` and the thematic functions through `callTheme`, so the phase 9 pages keep reading the same object as an `AnalyticsSource`.
- **Metric registry.** Every card names a metric of the web registry; the thematic cards add `sales_per_opening_hour`, `invoices_per_opening_hour`, `revpash`, `peak_share_top_hours` and `dead_hour_share`, and the display series `moving_average_net`, `month_net`, `store_net_share`, `hour_heat`, `busy_window` and, for So sánh, `store_day_index` and `store_day_gap` (with Năm's `since_opening_net`). Chất lượng dữ liệu adds `modifier_line_share` and `consent_coverage` and the display series `uncategorised_items`, `unverified_days`, `unclassified_payment_methods` and `store_findings`. Chart series take the tones `primary` to `quinary` (tokens `chart-1` to `chart-5`) and `muted`; a model series may ask for a dashed line (`dashed`), which So sánh uses from its sixth store on. Metrics with their own SQL function are kept out of `metric_value` (`ownFunctions` in `@fnb/metrics`).
- **Two CSV formats.** Every table downloads UTF-8 with a BOM through `buildCsv(columns, rows, dialect)` in `src/lib/csv.ts`. The comma format with decimal points is the default and byte for byte phase 9's output; the semicolon format writes decimal commas for an Excel set to Vietnamese. The choice is a per-device preference (`preferences.csvDialect`, provided by `CsvDialectProvider`), chosen in Cài đặt → Ngưỡng báo cáo under "Thiết bị này"; there is never a `sep=` line. `src/lib/csv-parse.ts` reads both formats strictly for the cost import of 10b.
- **Heat tables.** The hour × weekday heatmap is a table with `variant: "heat"`: one row per hour from the first to the last with sales (from the first selected store's day start), columns "T2" to "CN" and an average column outside the shades. `heatLevels` in the data table splits the heat columns' values into five quantile shades of the sequential tokens; money is compact in the cells and full in the CSV, and the table scroller keeps the hour column pinned at 360 px (ADR-035).
- **Dropping cached analytics.** `invalidateAnalytics(queryClient, tenantId)` (`src/data/invalidate-analytics.ts`) invalidates every analytics query of one tenant, whatever its source kind: a mounted query refetches at once and an unmounted one on its next mount, and another tenant's queries are left alone. It takes no source kind, because a tenant's queries come from one source at a time (the demo tenant is its own tenant).
- **Settings source and writes.** `src/settings/source.ts` defines a `SettingsSource` (membership, item types and roles, report settings, the catch-up status and a refresh chunk); `supabase-settings-source.ts` reads and writes through row-level security, and `demo-settings-source.ts` wraps the demo's settings store. A page writes through `useSettingsMutation(write, { touchesMappings })`: the write's error becomes a message of `WRITE_ERROR_KEYS`, and a success invalidates the tenant's settings queries, its cached analytics and Hôm nay's report, because phase 9's stale times would otherwise show rows read before the change (ADR-036). A write that touches a mapping also starts the catch-up. Since #105 the hook also hands the page `errorKey`: the store-code, opening-hours and frozen legal-text messages where they apply, the owner-only hours message when the refused change held opening hours. After a network failure it offers `retry`, which sends the same change again ([settings.md](settings.md#usesettingsmutation)).
- **The demo's settings.** The demo keeps one `DemoSettingsStore` of `@fnb/demo-analytics` per page load (`src/demo/demo-settings.ts`), in memory and reset on reload: the tenant and store profiles (opening hours, seats, opening date, e-invoice, receipt-numbering and member-feature statuses included; the tenant's legal form and default language), store accounts, roles, category and payment-kind overrides, costs, fee rates, targets, custom holidays, report settings and legal documents (the six kinds of the database, drafts, published and retired, with the database's version, language and length rules, one published text per kind and language, a new text always a draft, and a published or retired text never edited or deleted; one draft privacy notice of the skeleton's headings to start with, `legalDraftSkeleton`, labelled as `legalVersionLabel` suggests), each written with the database's checks and refused whole when one fails. A change to roles, category or payment-kind overrides, fee rates or store accounts bumps the store's ingest version, and the demo engine rebuilds its aggregates on its next call, so the demo needs no catch-up; custom holidays reach the reports and Hôm nay's baselines at once.
- **Catch-up after a mapping change.** `CatchUpProvider` (mounted once in the shell) owns the app's one runner: it reads `analytics_catch_up_status`, refreshes the newest 92 pending days at a time through `refresh_my_analytics`, and drops the tenant's cached analytics whenever the pending range moves. `CatchUpBanner` shows on every theme and settings page with "Cập nhật ngay" for owners and managers, and the pending range marks the cards as updating (ADR-036).
- **Theme parameters.** A theme declares its parameters as `ThemeParamSpec` entries of its definition: an id, a label key, the card it belongs to, a `select` or `radio` control, a default, and options that are either fixed or read from a call's rows (`optionsFrom`, with `accepts` checking a value the address carries before any row has arrived). `parseThemeParams` keeps a readable value and falls back to the default otherwise; the address then drops the parameter and is rewritten with a replace, as a range is. A value whose options come from a call and that the answered call does not offer (a shared link, or a range where that promotion did not run) is dropped the same way once the call has answered. An option may be disabled; a disabled value is never kept. A change made in the card pushes one history entry with the parameter in the address and reaches the definition through `ThemeContext.params`; only the calls whose arguments the parameter enters are asked again, because every other call keeps its query key. A radio button commits at once; a select commits after 700 ms without another change, on Enter or when it loses the focus, as the typed dates do, so stepping through its options with the arrow keys pushes one entry and asks for one call. `useCardsLoad` hands the page the rows of answered calls (`answered`: undefined while a call loads, none for a failed call), so a select waits with "Đang tải…" and is left out when its call failed or answered with no option. Khuyến mãi's two parameters live in `packages/reports/src/themes/promotions/params.ts`: `promo` (a select over the promotions of the `promotionsW92` call, the largest discount first and ties in code-point order of kind and key, each named with its kind, "Giảm giá hóa đơn không tên" for an unnamed one; a missing value shows the first) and `cmp` (`baseline`, `prior_weeks`, `sister_store`, a radio group), both on the `lift` card. `cmp` also reads the answered lift (`comparatorOptions`): when its summary row has no control store, `sister_store` is disabled with the reason "Mọi cửa hàng đang chọn đều chạy chương trình này nên không có cửa hàng để so sánh.", and a link asking for it is replaced by the default. `CardControls` keeps a parameter's last answered options while only that parameter changes (`paramOptionsScope`: the range, the stores and the other parameters), so the sister store does not flicker while a new comparator's lift loads; a parameter whose options are not known yet shows its fixed options.
- **Contracts of 10b.** `themeFunctions` holds the argument and row schemas of the nine 10b functions (`promotion_days`, `promotion_catalogue`, `promotion_lift`, `promotion_compliance`, `item_discount_days`, `shift_adjustments`, `data_quality_items`, `data_quality_summary`, `data_quality_payments`) after the build spec's signatures, and `ARGUMENT_SQL_TYPES` the SQL type of each new argument. The demo engine has a port of every 10b function, each held to the SQL by its parity file.
- **Message files of 10b.** `theme-promotions`, `theme-shifts`, `theme-stores`, `theme-quality`, `settings-store`, `settings-holidays`, `settings-manual` and `settings-legal` exist in both languages with their title keys and are registered in `catalog.ts` with their prefixes, so the later 10b tickets add keys to their own file and never edit the catalogue.
- **Size.** The theme pages are lazy routes (`src/pages/themes/<slug>/<slug>-page.tsx`, a lazy pattern of the size check); their message files are static, as the report files are. The entry chunk still holds no zod.

- **Data-subject pages (#254).** `#/khach-hang/tra-cuu-du-lieu` (`privacy-lookup-page.tsx`) looks a customer up by phone through `dsr_lookup` (POST body, masked result, never in the address or the console), lists the consent per purpose and withdraws `loyalty` or `marketing` after a confirmation (an update of `revoked_at` that `app.has_active_consent` reads at once, so the next promotional message is refused), and records a request linked to the customer. `#/khach-hang/yeu-cau-du-lieu` (`privacy-requests-page.tsx`) is the queue: each request with its type, status and two deadline badges coloured by `deadlineOf` (done, overdue, due within 3 days, on track; the same rule as `dsr_due_soon`, whose counts fill the banner), and for an open request the actions Tải dữ liệu (`dsr_export`, a private JSON file named after the request, never the phone), Sửa tên (`dsr_correct`, name only), Xóa khách (owners only; `dsr_deletion_preview` fills the confirmation with the counts, then `dsr_delete` shows the counts it logged and whether both deadlines were met) and Đóng yêu cầu (completed or rejected with notes). A request not linked to a customer can only be closed; the form says to record it from the lookup to export, correct or delete. Managers see a deletion request but get "Chỉ chủ quán xóa được khách."; staff, viewers and store-limited managers see no tab and, on the address, the reason (`privacyAccess`, `src/privacy/access.ts`). Sources: `PrivacySource` (`src/privacy/source.ts`, `supabase-privacy-source.ts`, in `CustomerSource.privacy`); live only, the demo says the section needs live data.

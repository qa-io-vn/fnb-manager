# `@fnb/zalo-mini`

Purpose and audience: what the two Zalo Mini Apps share, so that each app holds only its screens: the Native Storage adapter, the session client behind a small interface with a local stand-in, the data endpoint and a small Data API client, the Vietnamese and English translator, the React shell on zmp-ui, `app-config.json` per brand with its command line, the Vite plugin that builds for the browser or for the Zalo runtime and serves the `local` mode of `pnpm zalo:dev` behind an access guard, the size budgets, the mocked Zalo SDK and the Playwright design checks. For developers of the Mini Apps ([apps/zalo-staff](../../apps/zalo-staff/README.md), [apps/zalo-customer](../../apps/zalo-customer/README.md)) and for reviewers of Zalo's rules (ADR-022). Phase 13 (#208) and the client side of phase 14a (#212, #213, #217): built and tested in a browser and against the local stack; nothing has run inside Zalo yet, because the owner's Zalo accounts do not exist yet (#8).

Last updated 2026-11-19

## The brand theme

A `theme` in a Mini App row (the owner's private brand file, or `config/synthetic-brands.json`) looks like this; the values are the synthetic brand-3's, not any real brand's. Every field after `dark` is optional, and the file is checked against WCAG 2.2 AA at every build (`app-config --config <file> --list` reads it too).

```jsonc
	"light": {
		"surface": "#F5F0F6", "surface_raised": "#FFFFFF", "surface_sunken": "#E6DCE9", "ink": "#231A2B", "ink_muted": "#6C5D77",
		"line": "#DCCFE0", "accent": "#6B2D7B", "accent_ink": "#FFFFFF", "highlight": "#6B2D7B",
		"hero": "#6B2D7B", "hero_ink": "#F5F0F6", "tile": "#F5F0F6",
		// optional groups, each all or nothing, the same in "dark":
		"line_strong": "#9684A3", "badge": "#F0B84B", "badge_ink": "#231A2B",
		"positive": "#347B58", "positive_soft": "#E2F0E8", "negative": "#A8232F", "negative_soft": "#F9E3E5",
		"warning": "#7F5A00", "warning_soft": "#FBF0CF", "neutral_soft": "#ECE6EE",
		"inverse": "#231A2B", "inverse_ink": "#F5F0F6",
		"tone_1": "#7A3B8F", "tone_1_ink": "#FFFFFF", "tone_1_soft": "#EFE2F3",
		"art_plate": "#F5F0F6"
	},
	"dark": { /* the same keys */ },
	"wordmark": "QMB", "tagline_vi": "…", "tagline_en": "…", "kicker": "…",
	"shape": { "card": 20, "panel": 28, "control": 14, "field": 10, "tile": 8, "sheet": 28, "border": 1.5, "outline": 2, "shadow": false },

```

`app-config` refuses a colour that is not `#RRGGBB`, a group set in part or in one palette only, tones that are not numbered from 1 without a gap, an unknown field, a contrast below its rule and a shape or type value outside its bounds (`validateBrandThemeRow` names the field). A brand without the status group is checked against the design tokens' status colours. [docs/design-system.md](../../docs/design-system.md#24-brand-themes-of-the-mini-apps) lists every role, custom property and utility.

## The build plugin

`miniApp()` in an app's `vite.config.ts` reads these variables:

| Variable | Values |
|---|---|
| `VITE_ZALO_RUNTIME` | `browser` (default): `zmp-sdk` is replaced by the mocked SDK and the session by the stand-in. `zalo`: the real SDK and `zalo-session`; needs `VITE_BRAND_KEY`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` and a generated `app-config.json` |
| `VITE_MINI_APP_STAGE` | `development` (the dev server's default) or `testing` (a build's default). A Testing build fails when its output still contains one of the app's `developmentOnlyMarkers` |
| `VITE_BRAND_KEY` | the brand key; `brand-1` in a browser build without one |
| `MINI_APP_CONFIG` | the `app-config.json` to build from, `app-config.json` in the app's folder by default; a browser build without it uses the synthetic `brand-1` of `config/synthetic-brands.json` |
| `VITE_ZALO_SESSION` | `stand-in` (default) or `local`, the session mode of `pnpm zalo:dev`: the browser runtime with the real session client. `local` runs only on the dev server: a build, or the Zalo runtime, is refused |
| `ZALO_LOCAL_SESSION_URL`, `ZALO_LOCAL_ACCESS_TOKEN` | `local` only, both required: the loopback address of the local `zalo-session` and the mock Zalo access token the mocked SDK hands out |
| `ZALO_LOCAL_SUPABASE_URL` | `local` only: the loopback address of the local Supabase API. Without it the dev server reads `SUPABASE_URL` from the workspace root's `.env` and uses it when it is a loopback address; either way only for the proxy, never in the page |
| `ZALO_LOCAL_ACCESS_KEY`, `ZALO_LOCAL_TUNNEL_HOST` | `local` only: the access guard's key (22 to 128 base64url characters) and the Cloudflare quick tunnel's host name (`….trycloudflare.com`), which needs the key |

A stand-in dev server (the customer demo of `pnpm zalo:dev --app customer`) given `ZALO_LOCAL_ACCESS_KEY`, and optionally `ZALO_LOCAL_TUNNEL_HOST`, gets the same access guard, allowed host and hot reload off (`standInAccess`, `standInServerOptions`), without any proxy; a build ignores both.

In the `local` mode the dev server proxies `/functions/v1/zalo-session` to `ZALO_LOCAL_SESSION_URL` and, when a Supabase address is known, `/supabase/rest/v1/`, `/supabase/auth/v1/` and (for the staff app's photos) `/supabase/storage/v1/` to the local API without the `/supabase` prefix, so the page reaches everything through its own origin. An access guard runs before every middleware and every WebSocket upgrade. A loopback request without forwarding headers passes, unless a tunnel host is set. Any other request needs the key: a `GET` or `HEAD` with `?key=<key>` (compared in constant time) gets a page that sets an HttpOnly, `SameSite=Strict` cookie, `fnb_local_access` (with a tunnel host `__Host-fnb_local_access`, also `Secure`), and moves to the same address without the key; a request with that cookie passes; anything else gets 403, an upgrade included. With a tunnel host the dev server also allows only that host name and turns hot reload off. `pnpm zalo:dev --lan` and `--tunnel` set these variables; [docs/development.md](../../docs/development.md) has the commands and [docs/security.md](../../docs/security.md), section 4.9, the threats.

Every build targets ES2015, names its scripts `assets/<name>.<hash>.module.js`, sets the page title from `app-config.json`, refuses `echarts` and `zrender`, and writes `dist/app-config.json` with the app section and the lists of CSS, entry and preloaded scripts that Zalo loads.

### Listing assets (#267)

`listing` checks every listed Mini App (each customer one, and any row with listing fields) against Zalo's listing and review rules and prints the owner's checklist; it exits 1 when a problem is found and 2 on a usage error:

- **name** (the `title`): 3 to 50 characters, not in capitals only, without "App", "Mini App" or "Zalo", without emoji or special characters, and containing `owner_mark`, the part that identifies the business as the owner confirmed it;
- **description**: 20 to 500 characters, without a link;
- **category**: `FNB`;
- **logo**: a PNG file, square, on one solid, opaque background (no transparent or see-through pixel, the four corners one colour);
- **owner's checklist**, by hand: the logo is the brand's own mark with no QR code and no phone number; the owner confirmed the owner-identifying part; the description says what the Mini App does.

The listing fields live beside the `mini_apps` columns, never in `config/synthetic-brands.json`, which holds those columns only (a test keeps any Mini App id out of it): `config/synthetic-listings.json` adds `id`, `owner_mark`, `description`, `category`, `logo` (`config/logos/brand-<n>-customer.png`, synthetic marks) and `stores: [{code, name}]`, which the customer app's standee command reads. The owner's brand file (outside the repository) can carry the same fields on its customer row, or a `listings` list: `pnpm --filter @fnb/zalo-mini listing --config <brand file>`.

## Who uses it

`apps/zalo-staff` and `apps/zalo-customer`; CI's `mini-apps` job and `deploy-mini-apps.yml` call its budget check and, in CI, its `app-config` command; `pnpm zalo:dev` (`packages/zalo/src/local-dev/`) starts the staff app's dev server in its `local` mode, and with `--app customer` the customer app's (guarded stand-in demo, or `local` with `--live`). [development.md](../../docs/development.md), section 6, has the recipe "Add a Mini App screen".
